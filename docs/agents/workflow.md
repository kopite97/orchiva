# 작업 흐름

## 작업 시작

1. 현재 대화에서 요청한 결과, 범위, 제외 사항과 이미 주어진 실행 권한을 확인한다. 사용자의 명시적 지시가 프로젝트 기본 규칙보다 우선한다.
2. [프로젝트 규칙](repository-guidelines.md)과 [지침 지도](../../AGENTS.md)에 연결된 해당 경로 지침을 읽는다.
3. 현재 파일과 Git 상태를 확인하고 기존 변경을 보존한다. 제품 동작을 바꿀 때 [MVP 설계](../design/mvp-design.md)의 관련 절과 현재 코드를 대조한다.
4. 계획 기반 작업이면 [계획 규칙](../plans/AGENTS.md)과 [목록](../plans/README.md)을 읽고 적용할 계획·단계·완료 기준을 확인한다.
5. [검증 기준](validation.md)에서 변경에 필요한 검증을 선택한다. 실제 세션 생성·재시작·장애 주입 여부를 작업 범위에 명시한다.

## 계획과 실행 권한

- 계획 작성 요청은 문서 작성과 이를 위한 조사 범위다. 그 요청만으로 런타임 구현·실제 연동 시험을 시작하지 않는다.
- 사용자가 해당 계획 또는 범위의 구현을 지시하면 실행 근거를 기록하고 진행한다. 이미 허용된 범위의 구현·수정·검증에 같은 승인을 반복 요청하지 않는다.
- 작은 수정이나 문서 변경에 별도 계획을 강제하지 않는다. 사용자가 계획을 요청하거나 기존 단계별 개발을 이어갈 때 계획을 사용한다.
- 구현 중 새로운 범위가 필요하면 기존 권한으로 해결 가능한지 먼저 판단한다. 승인된 범위 안의 일반적인 구현 선택은 스스로 결정하고 계획에 반영한다.
- M0~M6 전체의 순서가 기록되어 있다고 전체 구현이 자동으로 시작되는 것은 아니다. 현재 요청한 단계와 권한을 따른다.

## 작업 중

- 검증된 PoC 증거와 개발 중 생성하는 결과를 분리한다. 이전 요청이나 결과를 지워 재시도를 쉽게 만들지 않는다.
- 설계와 구현이 달라지면 원인·영향을 해당 계획에 기록하고 관련 설계를 함께 갱신한다. 계획의 미구현 내용을 현재 기능으로 설명하지 않는다.
- 상태, 저장, 외부 호출을 바꿀 때 [소스 규칙](source-conventions.md)의 불변 조건을 확인한다.
- 현재 사용 중인 checkout을 우선 사용한다. 새 작업 폴더나 저장소 이전은 실제 필요와 사용자 지시에 근거한다.

## 완료 전

1. 변경 종류에 맞는 검증을 수행하고 명령·조건·결과·미검증 항목을 기록한다.
2. Git 변경과 이번 작업의 임시 산출물을 확인한다. 실패 증거·요청 JSON·검증 기준 파일을 임시 로그로 취급하지 않는다.
3. 계획 작업이면 완료 조건과 검증 결과를 대조하고 계획과 목록 상태를 함께 갱신한다. 문서 작성 완료와 구현 완료는 구분한다.
4. 변경 결과, 확인한 근거, 실제 남은 제약을 간결하게 보고한다. 원격 반영 여부와 로컬 저장 여부를 정확하게 표현한다.
