작성일: 2026-11-16 · Asia/Seoul. 소스: `C:/Dev/Orchiva`, `main`의 `3aad026` 이후 로컬 변경. 사용자 지시: “D3까지 필요한 GUI검증을 이제 진행해줘”, 화면 간섭 후 “지금 검증을 계속해 주세요”. 컴퓨터 유스로 실제 WinUI 앱을 조작했다. D4~D6는 수행하지 않았다.

**D1~D3의 GUI 수용 G01~G11을 완료했다.** 처음 남았던 트레이 복원/메뉴 종료와 125%·150% 글자 선명도는 같은 날 사용자 조작·확인과 도구 관측을 결합해 마무리했다. 실제 연동·합성 시험·사용자 확인의 범위는 아래 표를 따른다. D4~D6는 미착수이므로 전체 [계획](../plans/desktop-transition.md)은 `active`를 유지한다. 이전 [D1 비GUI 기록](desktop-d1-runtime-completion.md), [D2·D3 비GUI 기록](desktop-d2-d3-completion.md)은 당시의 이력이다.

125%·150%에서는 도구가 반환한 이미지의 글자 획이 일부 빠져 보였고 Windows 설정 화면에서도 같았다. 후속 검증에서 각 배율의 Orchiva를 앞에 띄운 뒤 사용자가 실제 모니터를 보고 각각 **“정상적으로 읽혀요”**라고 답했다. 따라서 해당 선명도 판정은 도구 이미지가 아닌 사용자 시각 확인을 근거로 한다. 200%에서는 도구로 글자와 하단 저장 버튼을 확인했다. 최종 배율을 시험 전의 **100%로 복원**한 화면을 확인하고 Windows 설정을 닫았다.

트레이 숨김 후 컴퓨터 유스의 대상 창 목록에는 작업 표시줄과 숨겨진 Orchiva가 나오지 않았다. 사용자에게 트레이 조작을 요청했고, “트레이 메뉴 열었어” 응답 뒤 원래 창 ID `265790`의 설정과 마지막 연결 정보가 복원된 것을 관측했다. 이후 사용자가 트레이의 ‘종료’를 선택하고 “종료했어”라고 확인했다. 앱 PID `32380`와 자식 bridge `16268`이 모두 사라졌고, 완료 요청 2건의 revision·결과 5개와 초기 합성 v2 3개의 해시가 유지됨을 대조했다. 메뉴 클릭 자체를 도구가 관측했다고 주장하지 않는다. [후속 보존·사용자 확인](../evidence/desktop-transition/d1-d3-gui-20261116/followup.json)을 따른다.

최종 배율 시험용 앱과 bridge도 정상 종료했다. 두 시험 daemon은 공개 `daemon stop --home ...`으로 종료했고 포트 51986/50074의 listener는 없다. 실행 원본과 장애 근거는 보존하며 정리 상태는 [cleanup](../evidence/desktop-transition/d1-d3-gui-20261116/cleanup.json)에 기록했다.

## 발견한 문제와 수정

1. 작은 창에서 고정 좌측 탐색과 가로 버튼 그룹이 공간을 차지했다. 자동 접힘 탐색, 줄바꿈 패널과 확인란을 적용하고 상단 상태와 스크롤 본문을 분리했다. 본문을 내려도 오류를 확인할 수 있다.
2. 4초 관측이 콤보를 비활성화해 선택 목록을 닫았다. 백그라운드 조회는 입력을 잠그지 않고, 드롭다운이 열린 동안 관측을 건너뛴다. 저장된 요청에서 갱신 주기를 넘겨도 목록이 유지됨을 확인했다.
3. 초기화 후 프로젝트 표시가 갱신되지 않았고 결과 근거는 JSON 이스케이프로 읽기 어려웠다. 프로젝트 라벨을 새로 읽고 최신 결과부터 한글 검사·파일·검토 이력을 표시한다.
4. 연결 실패와 복원 중에도 상단이 연결됨으로 남았다. 작업실의 연결 오류를 상위 상태에 전달하고, 복원 중 handshake에서는 작업실을 비활성화한다. capability를 다시 받은 재연결 후 활성화한다.
5. 다중 파일 선택 시 첫 파일의 비교가 계속 표시됐다. 새로 선택한 파일을 비교하고 파일명을 표시한다. 반영/이어 처리/undo 후에는 반영 이력과 선택 상태도 즉시 갱신한다.
6. 첫 PLAN에 계획 작성 단계의 도구/구현 금지가 제작 지시로 들어갔다. 계획 모델에는 snapshot의 로컬 읽기만 허용하고 계획 단계 제한을 향후 제작 PLAN에 옮기지 않도록 프롬프트를 명확히 했다. 기존 첫 PLAN은 시험 중 외부 편집·재확인 절차로 고쳤고 새 수정 요청의 AI PLAN으로 변경을 확인했다.

## 자동 검사와 남은 범위

`npm run typecheck` 통과, `npm test` 108/108, 격리 설정을 지정한 .NET bridge test 13/13, WinUI x64 build 경고·오류 0. GUI 수정본을 `.desktop-local/d1-20261116-gui-001/gui-build/Orchiva.Desktop.exe`에서 검증한 뒤 트레이 시험 앱 종료 후 기본 출력에도 재빌드했다. 후속 배율 검증은 최신 `desktop/Orchiva.Desktop/bin/x64/Debug/net10.0-windows10.0.26100.0/win-x64/Orchiva.Desktop.exe`와 합성 bridge에서 수행했다. 실제 빈 저장소 `desktop:verify -- verify d1-20261116-gui-empty`도 통과했다.

후속 앱 실행 첫 시도에서 에이전트가 로컬 `DOTNET_ROOT` 전달을 누락해 .NET Desktop Runtime 설치 안내가 표시됐다. 사용자가 안내를 닫았고, 이미 설치된 로컬 SDK의 WindowsDesktop runtime 10.0.12 경로를 자식 프로세스의 `DOTNET_ROOT`/`DOTNET_ROOT_X64`로 전달해 정상 실행했다. 전역 런타임 설치·환경 변경은 에이전트가 수행하지 않았다. 이 사건은 최종 배포 완료의 근거가 아니며 D6 설치·배포 검증은 별도다.

주 요청은 Node 자동 검사 profile을 사용했고 통과→의도적 실패→복구 통과를 기록했다. 수정 요청은 파일 근거 profile로 자동 명령 검사는 0개다. 별도로 `alpha.txt=616c7068610a`, `beta.txt=626574610a`, `answer.txt=34320a` 바이트를 대조했으며 모델이 보고한 테스트와 제품의 자동 검사 결과를 혼동하지 않았다.

D1~D3 GUI 수용의 남은 항목은 없다. D4~D6는 미착수이며 이번 변경은 로컬 소스·문서에만 저장했다. commit/push하지 않았다.
