# M0 실행 기반 검증과 결정

작성일: 2026-11-12 · Asia/Seoul

## 결과

M0의 브라우저 없는 Plugin 연결, 고정 커밋 Worktree 생성, 생성 응답 유실 후 대조, 연결 종료, 시험 클라이언트 강제 종료를 실제 환경에서 확인했다. 타입 검사와 27개 테스트, 기존 `verify`·`verify:lifecycle`이 통과했다. 운영용 백그라운드 요청 처리 루프는 M3 범위로 남긴다.

핵심 제약은 **daemon 재시작 뒤 provider 이력에서 `clientMessageId`가 없어질 수 있다는 것**이다. 메시지 내용은 남아도 그것만으로 원래 전달 키를 확정할 수 없다. 따라서 복구 전달이 미확정이면 `needs-input`에 보존하고 자동 재전송과 다른 키의 새 재개를 차단한다.

| 환경 | 값 |
| --- | --- |
| 소스 기준 | 초기 커밋 `7a675a918408419e5a245da4e086c04bced4716c` |
| sandbox 기준 | 지침 연결 커밋 `86e00e0c80cc0822eaa2e5e70b406530f7c7749a` |
| 도구 | Windows, Node 24.19.0, npm 11.17.0, Git 2.55.0.windows.5 |
| Paseo | daemon·Plugin SDK·client 0.15.4 |
| 시험 전용 전송 프록시 | 이미 설치된 버전과 같은 `ws` 8.22.2를 직접 개발 의존성으로 명시 |
| 실제 시험 | `m0-20261112-foundation-001` |

요약 증거는 [M0 증거 JSON](../evidence/m0-foundation-20261112.json)에 보관한다. 로컬 원본 manifest, Plugin 이벤트, 미확정 체크포인트와 시험 Worktree는 보존했다. 인증값과 요청 JSON 전체는 소스 저장소에 포함하지 않는다.

## 연결과 종료

`createHostClient`와 `createPaseoApi`를 소유하는 `OwnedConnection`을 도입했다. 시작 호출을 공유하고, 연결 실패 시 기존 리소스를 닫은 뒤 제한된 횟수로 다시 연결한다. dispose는 대기·연결 시도를 취소하고 API와 client를 해제하며 반복 호출에도 같은 종료 작업을 사용한다. 종료 후 다시 시작할 수 없다.

Plugin의 로컬 시험 설정이 있을 때만 `startM0Probe`가 초기화 직후 읽기 전용 관측을 시작한다. 설정이 없으면 연결·타이머를 만들지 않는다. 다섯 세대 모두 첫 관측 당시 Plugin RPC 호출 수가 0이었고, 세 번의 연속 reload와 두 번의 cold start에 해당하는 기록을 확보했다. 최종 해제 후 다섯 세대 모두 `closed`이며 추가 기록이 생기지 않았다.

연결 불가와 종료 중 재접속 취소는 모의 테스트와 실제 닫힌 로컬 포트에서 확인했다. 운영 중 자동 재접속·전체 요청 순회는 아직 구현하지 않았다.

## 고정 커밋

Worktree 생성 API의 `source.refName`에 완전한 SHA를 전달할 수 있다. 생성 전 커밋 존재를 확인하고, 생성 후 sandbox 소속과 실제 HEAD를 대조한다. 시험 전용 ref를 `47c21d4`에서 `86e00e0`으로 옮긴 뒤에도 미리 확인한 `47c21d4`에서 Worktree가 생성되는 것을 확인했다. 시험 ref는 비교 후 제거했고 `main`은 이동시키지 않았다.

`createPinnedWorkspace`는 이 경로를 제공한다. 기존 PoC의 `request.start` 전체 흐름을 새 계획 승인 계약으로 전환하는 작업은 M2에 남긴다.

## 생성과 전달

로컬 WebSocket 프록시로 서버의 응답 프레임을 SDK에 전달하기 전에 버렸다. workspace·agent·message 각각 호출자의 Promise가 미완료인 상태에서 별도 연결로 실제 효과가 존재함을 확인했다. 인증 정보는 프록시 메모리에서 전달만 하고 기록하지 않았다.

| 대상 | 재시작 후 관측 | 채택할 정책 |
| --- | --- | --- |
| workspace 생성 | 동일 키 재호출이 동일 workspace ID를 반환. 해당 요청의 리소스 수 1 유지 | 의도·키·내용 해시를 먼저 저장하고 리소스 관계·HEAD를 대조 |
| agent 생성 | 동일 키 재호출이 동일 agent ID를 반환. 동일 workspace 관계와 수 1 유지 | 세션 식별자와 생성 의도를 보존하고 새 세션을 만들기 전에 대조 |
| 메시지 전달 | 재시작 전 `clientMessageId` 조회 성공, 복원 후 일부 이력에서 식별자 소실 | ID가 확인되지 않으면 `unknown`. 텍스트 일치를 전달 확정으로 사용하지 않음 |
| 다른 입력과 같은 키 | 기록된 충돌 시험에서 workspace·agent·message 모두 호출 거부 | 실패 원인까지 일반화하지 않으며 Orchiva 명령 계층에서도 입력 해시 검사 |

메시지 동일 키 재호출의 통제된 시험에서는 사용자 메시지가 추가되지 않았다. 이는 특정 버전·사례의 관측이며 메시지 ID 소실을 무시한 범용 자동 재전송 보장으로 확대하지 않는다. 불확실한 복구의 자동 재전송은 비활성화했다.

`findMessage`는 이전 timeline 페이지까지 검색한다. 페이지 예산 초과, 끊긴 이력, epoch 변화, 조회 실패, client ID 없는 복원 이력은 `unknown`이다. `absent` 역시 그 자체로 안전한 재전송 허가가 아니다. 공통 효과 체크포인트는 기본적으로 부재 상태의 재시도를 막고, 호출자가 별도 검증한 조건에서만 허용한다. 이 도우미는 직렬 호출을 전제로 하며 M1의 명령 저장소·잠금을 대체하지 않는다.

## 강제 종료와 안전한 대기

별도 Node 시험 클라이언트가 메시지 응답을 받은 뒤, 로컬 완료 기록을 저장하기 전에 부모가 그 자식 PID만 강제 종료했다. daemon 재시작 뒤 체크포인트는 유지됐으며 원래 시험 메시지 내용은 한 건이었다. client ID가 복원되지 않아 전달 상태는 `unknown`으로 남겼고 추가 전송은 하지 않았다.

실제 복원 세션과 별도 시험용 `JsonRequestStore`를 연결하여 `TrackExecution.refresh`를 두 번 수행했다. 상태 `needs-input`, 시도 2, pending 복구를 유지했고 새 키의 재개를 거부했다. 전후 timeline이 동일하여 실제 메시지가 추가되지 않았음을 확인했다.

## 기존 PoC 증거 대조

완료 판정된 성공·실패 복구 두 요청은 검증 대상 JSON 투영의 해시가 동일했다. 기존 실패 결과·판정·시도 번호와 검사 파일을 보존했고 원래 테스트도 다시 통과했다. 실패 복구 검사의 실제 파일 SHA-256은 기존 값 `ac419489fa43b8ab51e67c33cd6df419abcab32cbc465745cb03ec53dba4a3aa`와 일치한다.

초기 RPC·GUI 두 요청은 기존 `request.list`가 복원된 timeline을 새 결과로 수집하여 **미승인 최신 결과 envelope가 교체됐다**. 요청·세션·workspace ID, PLAN 파일과 `POC_PROOF.md`·`GUI_PROOF.md`는 일치하고 검토 대기 상태를 유지했다. 두 건의 이전 결과 envelope는 사전 원본 백업이 없어 복원하지 못했다. 전체 JSON이 그대로 보존됐다고 표현하지 않는다.

이 차이는 원래 해시를 덮어쓰지 않고 manifest의 `legacyRefresh`에 전후 해시·새 결과 ID·사유로 기록했다. 새 `init`은 원본 요청 JSON도 로컬 `original-requests`에 저장하도록 보강했다. 이번 실행의 회귀 이후 원본은 별도 `post-regression-requests`에 보존했다. 결과를 불변 이력으로 관리하고 조회와 수집을 분리하는 작업은 M1·M3에서 해결한다.

보강한 백업 경로는 별도 `m0-20261112-snapshot-001` 실행에서 확인했다. 현재 요청 4건과 백업의 바이트 SHA-256이 모두 일치했다. 이는 회귀 이후의 백업 검증이며 앞선 결과 envelope를 복원한 것은 아니다.

## 재검증과 정상 상태

소스 루트에서 `npm run m0 -- help`로 명시적인 시험 명령을 확인한다. 인수 없이 실행해도 생성·중단 시험을 시작하지 않는다. 보존된 실행은 아래 명령으로 확인할 수 있다.

```powershell
npm run typecheck
npm test
npm run m0 -- verify --run-id m0-20261112-foundation-001
npm run m0 -- verify-uncertain --run-id m0-20261112-foundation-001
npm run m0 -- probe-report --run-id m0-20261112-foundation-001
```

새 시험은 새 run ID로 `init`을 수행하고 각 단계를 명시적으로 실행한다. `fault-*`, `crash`, `replay`, `conflicts`, `base-ref`는 실제 효과를 만드는 시험이다. 기존 실행의 `init`을 덮어쓰거나 다른 실행의 프로세스를 종료하지 않는다. daemon 재시작 전 `assert-idle`로 관측 가능한 모든 작업이 멈췄는지 확인한다.

완료 시 `m0-probe.json`은 제거했고 Plugin은 정상 모드로 reload했다. 시험 생성 리소스와 미확정 증거는 보존했으며 활성 turn은 없다. 원격 push·merge는 수행하지 않았다.

## 후속 단계에 전달할 사항

- M1: 의도·입력 해시·외부 ID·pending/unknown을 저장하고 기존 결과·판정을 불변 이력으로 옮긴다. 작업별·프로젝트별 잠금을 구현한다.
- M2: 확인한 `baseCommit`을 실행에 전달하고 변경된 계획을 거부한다.
- M3: 이번 연결 소유 구조에 재접속·시작 대조·조회와 수집 분리를 연결한다. 시험 observer를 운영 스케줄러로 그대로 확대하지 않는다.
- M5: 메시지 ID가 소실됐을 때의 사용자 확인 절차를 설계한다. 텍스트 유사성이나 시간 경과로 미전송을 추정하지 않는다.
