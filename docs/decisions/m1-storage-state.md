# M1 저장과 실행 제어 결과

작성일: 2026-11-12 · Asia/Seoul · 기준 소스: `4397aaf`

## 결과와 적용 범위

[M1 계획](../plans/m1-storage-state.md)에 따라 v2 저장·마이그레이션, 불변 결과·판정 이력, 명령 이력, revision 검사, 프로세스 소유권과 단일 실행 슬롯을 구현했다. M0에서 관측한 최신 결과 덮어쓰기를 막기 위해 목록 조회의 외부 관측·검증도 제거했다. 화면은 기존 PoC 계약을 유지한다.

실제 기존 4건을 백업 후 변환했고, 기존 필드 전체의 정규화 비교가 일치했다. 결과 5건(실패 복구의 이전 결과 포함), 판정 2건을 보존했다. 완료 2건과 검토 대기 2건의 상태를 바꾸지 않았다. 원래 실패 검사 파일 SHA-256도 `ac419489fa43b8ab51e67c33cd6df419abcab32cbc465745cb03ec53dba4a3aa`로 유지됐다.

실제 실행 ID는 `m1-20261112-storage-001`이다. 비밀값 없는 [검증 요약](../evidence/m1-storage-20261112.json)을 저장했고, 로컬 원본과 실행별 보고서는 `%USERPROFILE%\.orchiva\m1\m1-20261112-storage-001`에 보관한다. 요청 원본과 인증값은 Git에 넣지 않는다.

## 저장 계약

요청별 JSON 하나에 `schemaVersion: 2`, 의미 변경용 `revision`, `updatedAt`, 조건·계획 출처, `results`, `decisions`, `attemptHistory`, `commands`를 저장한다. 기존 `result`, `decision`, `attempts`와 평면 상태는 현재 화면·RPC의 호환 필드다. 이력이 원본이며 호환 필드를 초기화해도 과거 이력은 제거되지 않는다.

- `results`: 기존 수집 정보에 `attemptNumber`, `validationRun`, `legacy`를 붙인다. 같은 ID의 내용 변경과 과거 결과 삭제를 거부한다.
- `decisions`: 고유 ID, 결과 ID, 확인 당시 지문, 승인 여부·근거·시각·legacy 여부를 보존한다. 수정 요청 판정도 재개 이후 남는다.
- `attemptHistory`: 시도 번호, 최초/재개/legacy 출처, 알 수 있는 수정 지시와 결과 ID를 연결한다. 재검증은 같은 시도에 결과만 추가한다.
- `commands`: 키, 종류, 입력 해시, pending/applied/failed/unknown, 단계, message ID, 리소스 ID, 원래 결과 참조와 시각을 보존한다. 완료 명령을 덮어쓰지 않는다.
- 계획·조건: 기존 자유문장은 `legacy` 조건 하나로 보존한다. 실행 전 확인이 없던 기록에는 `legacy-execution` 또는 신규 PoC의 `poc-direct` 출처를 쓴다. 확인하지 않은 base SHA나 세부 조건 판정을 만들어내지 않는다.

저장은 project→request→write 순서의 잠금을 사용한다. `revision`이 오래되면 `REVISION_CONFLICT`, 기존 이력 변경은 `IMMUTABLE_HISTORY`로 거부한다. 단순 관측 오류 갱신은 의미 revision을 올리지 않는다. 저장 직전 스키마·참조를 검사하고 임시 파일 sync 후 rename한다. 이는 프로세스 중단을 다룬 검증이며 전원 장애 내구성이나 여러 PC의 공유 디렉터리 트랜잭션 보장은 아니다.

## 마이그레이션과 진단

버전 없음/1은 v1이며, 변환 전 원본 바이트를 `requests/backups/v1/<token>-<sha256>.json`에 배타적으로 저장한다. 기존 백업이 있으면 동일 바이트인지 대조하고 덮어쓰지 않는다. backup 직후와 rename 직전에 중단된 경우 원본은 남고 다음 실행이 같은 백업에서 변환을 완료한다. `.tmp`는 정식 요청으로 읽지 않는다.

손상 JSON, 미래 버전, token 불일치는 해당 파일을 그대로 두고 정상 파일 목록을 반환한다. `storage.diagnostics`는 문제 파일명·오류 코드, 요청 수·바이트 수·결과/판정 수·점유 요청을 반환한다. 진단 문제가 있으면 빈 슬롯이라고 추정하지 않고 새 효과를 차단한다.

M0 이전에 이미 사라진 초기 두 결과 envelope는 이번 변환으로 복원되지 않는다. 마이그레이션 원본은 이번 작업 시작 때 존재하던 데이터이며, 원본 필드가 동일함을 전체 정규화 비교와 바이트 백업으로 확인했다. `migration.missingHistory: true`는 과거 이력이 완전하다고 주장하지 않는 표시다.

## 실행 소유권과 명령

Windows 데이터 디렉터리 실경로의 SHA-256으로 결정한 named pipe를 독점 소유한다. 다른 Plugin/프로세스의 bind는 실패하고 그 인스턴스의 RPC·Hook은 저장소 준비 오류로 실행되지 않는다. 정상 종료는 처리 중인 명령을 마친 뒤 소유권을 반환한다. 강제 종료에서는 OS가 소유권을 회수한다. PID 나이·타임아웃만으로 다른 소유자의 잠금을 지우지 않는다. 비 Windows fallback은 검증하지 않았다.

슬롯은 별도 파일이 아니라 저장된 요청 상태·미확정 명령에서 복원한다. 준비·실행·질문 대기·검증·pending/unknown은 점유하고 확정된 완료·검토 대기·실패는 해제한다. 다른 요청이 점유하면 `BUSY`에 해당 token을 포함한다. 재개와 재검증도 같은 검사를 한다. 복수 기존 점유가 발견되면 새 효과를 차단하며 운영 중 자동 대조는 M3 범위다.

같은 명령 키는 revision 검사 전에 조회하며, 다른 입력 해시는 거부한다. 과거 재개 키를 다시 보내도 새 시도가 생기지 않는다. 원래 결과는 `outcomeRef`와 결과 이력으로 확인할 수 있다. workspace·agent 생성 응답이 불확실하면 동일 키를 무조건 재호출하지 않고 unknown으로 남긴다. M0 메시지 대조 정책도 그대로 유지한다.

`request.revalidate`는 `commandKey`, `resultId`, `expectedRevision`을 받으며 중복 검증을 방지한다. 기존 PoC 버튼의 `request.refresh(revalidate: true)`도 유지하지만 실행 중/전달 대기는 관측만 수행한다. 기존 RPC의 revision 없는 호환 호출은 계속 허용하므로, 모든 UI 명령에 revision을 요구하는 전환은 해당 화면을 만드는 M2·M4·M5에서 완료한다.

## 검증 근거와 수정한 문제

| 항목 | 실제 결과 |
| --- | --- |
| V01 | 모의 v1과 실제 4건 변환, 바이트 백업·ID·결과·판정·실패 검사 유지 |
| V02 | backup 후/rename 전 예외 주입, 원본 유지·재실행 완료·중복 백업 없음 |
| V03 | 손상·미래·token 불일치 격리, 오래된 revision·이력 변조·삭제 거부 |
| V04 | 재검증·수정 요청 판정·두 번 재개 후 모든 결과와 판정 유지 |
| V05 | 과거 키 replay·다른 입력 충돌·unknown 보류·재검증 명령 중복 제거 |
| V06 | 다른 유스케이스 두 동시 시작 중 하나만 Worktree/agent 효과, 재시작 뒤 BUSY 유지 |
| V07 | Windows 실제 자식 프로세스 종료 후 소유권 재획득, 실제 Plugin 소유 중 두 번째 writer 거부 |
| V08 | 실제 Plugin reload, 반복 목록·진단 4회에서 요청 쓰기 0, 기존 verify 두 종류 통과 |
| V09 | 타입 검사·40개 테스트·스크립트 문법·문서 정합성 검사 |

신규 모델 실행은 하지 않았다. 동시 실행 효과 수는 모의 runtime과 실제 파일 저장으로 확인했고 프로세스 소유권은 실제 Windows 프로세스로 시험했다. 실제 Plugin의 마이그레이션·순수 조회·reload·회귀 검증은 별도 수행했다.

최종 정적 문서 검사는 Markdown 17개, 로컬 링크 73개, 인코딩·코드 블록·계획 상태·증거 정합성을 확인했다. `git diff --check`도 통과했다. sandbox 소스 작업 트리는 변경하지 않았다.

초기 검증에서 다음 문제를 확인하고 고쳤다.

1. 기존 테스트는 agent 응답 유실을 실패로 보고 자동 재호출했다. M0의 unknown 정책에 맞게 동작과 기대값을 변경했다.
2. 자식 소유권 시험이 준비 신호 직후 종료되어 경합을 재현하지 못했다. IPC 수신 대기로 시험 프로세스를 유지한 뒤 명시적으로 종료했다.
3. loopback 포트 해시가 실제 사용 중 포트와 충돌했다. Windows에서는 경로 기반 named pipe로 변경했다.
4. 설치된 SDK 0.15.4가 비동기 contribution 반환을 거부했다. 동기 등록 후 모든 RPC·Hook이 `ready`를 기다리게 바꿨고 실제 reload에 성공했다. 실패했던 적용에서도 사전 백업과 v2 기록을 보존했다.
5. PoC 새로고침은 관측과 재검증을 합쳐 호출한다. 전달 대기에서 이를 막으면 대조도 불가능하므로 기존 호출은 관측으로 처리하고 별도 재검증 명령만 엄격히 검사한다.

## 재검증과 다음 단계

```powershell
npm run typecheck
npm test
npm run m1 -- verify m1-20261112-storage-001
npm run verify
npm run verify:lifecycle
```

첫 두 명령은 소스만으로 실행한다. 나머지는 이 PC의 실행 기록과 Plugin daemon이 필요하다. `backup`은 새로운 v1 원본과 새 실행 ID에만 사용하며 기존 실행을 덮어쓰지 않는다.

M2는 초안·계획 확인·고정 SHA 실행을 구현한다. M3는 목록 페이지네이션·백그라운드 대조·조회와 수집의 구분을 완성한다. M4는 상세 파일/검사 증거와 조건별 판정, M5는 미확정 전달의 사용자 해결·초기 재시도 화면을 구현한다. M1은 현재 PoC 화면의 기존 흐름을 유지하는 저장·실행 기반이며 MVP 전체 완료를 의미하지 않는다.
