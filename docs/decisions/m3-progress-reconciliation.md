## 운영 수명과 복원 정책

`Reconciler`는 타이머와 진행 중 cycle 하나, 소유 연결 하나, Hook 힌트 큐를 관리한다. 초기 store 소유권·마이그레이션이 끝나면 화면과 무관하게 시작한다. Hook은 힌트를 넣고 즉시 반환하여 모델 턴과 프로젝트 잠금 사이의 대기를 피한다. 정상 주기는 5초이며 Hook이 있으면 앞당긴다. cycle은 겹치지 않는다.

연결 생성에는 M0 `OwnedConnection`을 사용한다. 연결 실패 시 기존 소유자를 닫고 5/10/20/30초 backoff 뒤 새 연결을 만든다. 초기 연결 자체의 제한된 재시도 시간과 API 지연은 주기와 별도다. 요청 관측 오류에는 같은 backoff를 적용한다. 서비스 상태·마지막 성공·다음 연결 시도는 `runtime.status`와 로컬 `runtime-status.json`에 기록한다. 로컬 상태 파일은 진단용이며 요청 저장의 권위 원본은 아니다.

초기 대조가 끝나기 전에는 새 시작을 거부한다. 이미 저장된 같은 시작 명령의 재호출은 이 gate보다 먼저 반환한다. 실행 슬롯·손상 파일 검사는 M1 정책을 유지한다. 종료는 타이머/Hook 중단 → 소유 연결 종료 → 진행 중 cycle drain → store 해제 순서다. 연결 close가 실패해도 종료 상태와 store 정리를 수행한다.

| 저장 checkpoint | 복원 동작 |
| --- | --- |
| start `accepted` | 확인한 계획·SHA·설정으로 준비 진행 |
| start `plans`, Workspace ID 있음 | 동일 PLAN 내용 확인 후 기록·세션 생성 진행 |
| start `workspace` 또는 `agent` 호출 중단 | `unknown`·`needs-input`·슬롯 보존, 생성 재전송 없음 |
| 실행 중·질문 대기·검증 중, Agent ID 있음 | 같은 ID를 관측하고 종료 시 수집 |
| pending 재검증 | 관측 실패 동안 원래 명령/결과를 유지하고 연결 회복 후 같은 명령에 새 결과 연결 |
| pending 재개 전달 | M0의 식별자 대조 정책 유지. 확인되지 않으면 재전송 없음 |

프로젝트 설정이 접수 이후 달라지면 준비 worker는 실패를 남긴다. 저장된 실행 입력을 새로운 설정으로 바꾸지 않는다. 초기 실패 재시도와 unknown 사용자 해결은 M5 범위다.

## 관측과 결과 보존

요청의 선택적 `observation`은 마지막 시도/성공 시각, 연속 실패 수, 다음 시도 시각과 오류를 보존한다. 관측 메타데이터만 바뀌면 revision·의미 갱신 시각을 올리지 않는다. 같은 내용 저장도 생략한다. 오래된 요청은 읽기만 해도 observation 필드를 추가하여 다시 쓰지 않는다.

주기 대상은 실행 슬롯을 점유하거나 아직 결과가 없는 실행 요청이다. 검증이 끝난 검토 대기·확정 실패·완료는 계속 검증하지 않는다. 외부 세션 변화는 Hook 또는 명시적 **상태 확인**으로 대조한다. 완료한 요청은 기존 판정을 유지한다. 파일만 외부에서 바뀌는 경우의 자동 감지·조건별 판정은 M4다.

관측 오류를 실행 실패로 바꾸지 않는다. 특히 `validating` 재시작 때 통신이 끊겨도 그 상태를 유지한다. 실제 증거 수집 실패는 실패로 구분한다. 같은 sourceKey의 중복 완료 Hook은 검사를 다시 실행하지 않는다. 뒤늦게 확정된 취소 사유가 오면 이전 결과를 보존한 새 결과 버전으로 정정한다.

## 화면과 조회 계약

- `request.page`: 전체/초안(ready 포함)/진행 중/확인 필요/완료 필터, 최신 의미 갱신 시각·token 순서, 최대20건 cursor. 제목·상태·시도·시각·허용 행동 요약과 별도 진행 중 목록을 반환한다. PLAN·결과·로그를 포함하지 않는다. 동시 변경을 동결한 snapshot pagination은 아니다.
- `request.detail`: 요청과 상태별 `allowedActions`. 읽기만 하며 결과를 수집하지 않는다. `request.list`·`request.get`은 기존 계약을 보존한다.
- `runtime.status`: 독립 관측 연결·복원 상태. 15초 이상 성공이 없거나 화면 연결이 끊기면 마지막 저장 상태와 지연 안내를 표시한다.
- 상세: 진행 단계·경과 시간·마지막 관측·최근 이벤트·접힌 작업 정보, 기존 결과 검토, 시도/검증 회차/판정 이력. 탭 이동 중 검토 메모를 유지한다.
- **상태 확인**과 **검증 다시 실행**을 분리했다. 상태 확인·목록 새로고침은 같은 결과의 검사를 다시 실행하지 않는다. 기존 단일 완료 판정은 유지하며 조건별 근거 판정·과거 결과 상세 선택은 M4다.

M2 검증 스크립트도 비동기 접수 후 Agent/결과를 기다리고 읽기 전용으로 확인하도록 수정했다. 이후 별도 실행이 추가돼도 시험 소유 제목·ID로 정확히1개를 대조한다. 기존 실제 M2 증거 파일과 결과는 변경하지 않았다.

## 재검증과 후속 범위

보존된 같은 PC에서 `npm run m3 -- verify m3-20261112-reconcile-001`을 실행한다. 새 시험은 `npm run m3 -- help`에 따라 별도 ID로 init → start → 소유 Plugin 재등록 → wait → checkpoint → idle daemon 정상 재시작 → verify 순서다. wait는 디스크만 읽는다. checkpoint 전에 무관한 활성 세션이 없는지 검사한다.

M4에는 조건별 검토·파일 지문 변화 표시·검사 오류 분류·과거 결과 상세, M5에는 초기 실패 재시도·unknown 해결, M6에는30분 운영·100건/30회 성능 측정과 전체 수용 시험이 남는다. JSON 파일을 읽어 요약하는 현재 방식의 대규모 성능은 아직 주장하지 않는다. 재연결 시간은 API timeout과 초기 연결 재시도에 영향을 받으며 서비스 주기만으로 전체 응답 시간을 보장하지 않는다.
