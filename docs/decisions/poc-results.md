# Orchiva PoC 결과 보고서

작성일 및 검증 기준일: 2026년 11월 12일 · Asia/Seoul  
대상: 프로토타입 MVP의 범위와 구현 방향을 결정하는 프로젝트 담당자

## 결론

**Paseo Plugin과 Codex를 연결해 단일 작업을 실행하고, 결과를 검증한 뒤 완료 판정 또는 실패 복구까지 이어가는 핵심 흐름을 확인했다.** 실제 성공 사례와 의도적으로 실패시킨 사례를 실행했으며, 실패 작업은 같은 세션과 Worktree에서 수정하여 원래 테스트를 통과했다. 완료 판정과 실패 증거는 daemon 재시작 후에도 유지됐다.

따라서 단일 작업 흐름을 출발점으로 **프로토타입용 MVP 설계에 진입할 수 있다.** 이번 결과는 작은 Node.js 작업을 대상으로 한 기능 타당성 검증이다. 다중 작업 스케줄링, 장시간 운영, 범용 빌드와 배포의 신뢰성까지 검증한 결과는 아니다.

## 목적과 검증 범위

Orchiva는 사용자의 기능 요청을 실행 가능한 작업으로 연결하고, 작업이 어디까지 진행됐으며 어떤 근거로 완료됐는지 추적하는 도구다. 이번 PoC에서는 다음 질문을 검증했다.

| 검증 질문 | 확인한 결과 |
| --- | --- |
| 구조화된 요청을 계획과 실행으로 연결할 수 있는가 | 여섯 입력 항목에서 REQ와 TASK, 두 PLAN을 만들고 Codex에 전달했다. |
| 요청별 작업 공간을 분리할 수 있는가 | 대상 저장소의 별도 Git Worktree와 브랜치를 만들고 세션을 연결했다. |
| 세션 생성 이후의 진행과 결과를 추적할 수 있는가 | 실행 상태, 최종 응답, 변경 파일, 독립 검증 결과를 수집했다. |
| 실행 종료와 작업 완료를 구분할 수 있는가 | 자동 검증 이후 검토 대기를 거쳐 근거가 있는 명시적 판정을 저장했다. |
| 실패한 작업을 맥락과 증거를 유지하며 재개할 수 있는가 | 같은 세션과 Worktree를 사용하고 이전 실패 결과를 보존했다. |
| 재호출과 재시작이 중복 작업을 만들지 않는가 | 검증 사례의 시작·복구 요청 재호출과 daemon 재시작 후 동일 실행 정보를 확인했다. |

구현 대상은 Windows의 로컬 Paseo daemon 한 개와 Plugin 인스턴스 한 개다. 각 요청은 TASK 하나와 Worktree 하나에 대응한다. 원격 저장소는 `kopite97/PoC-sandbox`로 제한했고, RNG는 사용하지 않았다. 원격 push와 merge는 수행하지 않았다.

## 구현된 사용자 흐름

사용자는 Title, Goal, Scope, Constraints, Validation, Completion Criteria를 입력한다. 선택적으로 Node 테스트 파일 경로나 파일에 포함되어야 할 문자열을 등록할 수 있다.

```text
Feature Request
  → REQ와 Request PLAN 생성
  → TASK와 전용 Worktree 생성
  → Task PLAN 기록 및 Codex 실행
  → 상태 추적과 결과 수집
  → 독립 검증
      통과 → 완료 조건 검토 → 완료 확정
      실패 → 원인과 증거 확인 → 재개 지시 → 같은 작업에서 재실행
```

PLAN은 입력 항목을 정해진 형식에 넣어 생성한다. 여러 TASK로의 자동 분해, 계획의 대화형 수정이나 계획 승인 화면은 이번 구현에 포함하지 않았다.

### 실행 상태와 완료 판정

| 상태 | 의미와 처리 |
| --- | --- |
| `planned`부터 `started`까지 | 계획 생성, Worktree 준비, PLAN 기록, 세션 생성 단계다. `started`는 세션 생성 성공을 뜻한다. |
| `running` | Codex가 작업을 실행하고 있다. |
| `needs-input` | 권한 대기 또는 복구 지시의 전달 여부 확인이 필요하다. |
| `validating` | 최종 응답과 파일 증거를 수집하고 등록된 검사를 실행한다. |
| `awaiting-review` | 수집된 실행 결과와 검사가 실패하지 않아 완료 조건 검토를 기다린다. 자동 검사가 없는 요청도 수동 검토 대상으로 이 상태가 된다. |
| `completed` | 해당 결과에 대한 완료 판정과 근거가 저장됐다. |
| `failed` | 실행·검증에 실패했거나 검토에서 수정 요청을 받았다. 원인에 따라 초기 실행 재시도 또는 기존 세션 재개를 사용한다. |

상태는 Paseo의 실행·권한 Hook과 화면의 2초 간격 조회로 동기화한다. daemon 재시작 중 놓친 Hook은 다음 화면 또는 RPC 조회에서 현재 실행 정보와 대조해 보완한다.

화면에서 완료를 확정하려면 완료 조건 확인과 판정 근거 입력이 필요하다. 서버는 결과 ID, 현재 실행 정보, 파일 지문을 다시 확인해 오래된 결과에 대한 판정을 거부한다. `completed`는 검증 당시 결과에 대한 판정 기록이며, 이후 모든 파일 상태를 계속 보증하는 표시는 아니다.

### 결과 수집과 실패 복구

각 결과에는 Codex 최종 응답, 변경 파일 목록, Git diff 요약, 파일 지문, 검사별 성공 여부·종료 코드·출력·소요 시간과 실패 원인을 저장한다. 새로 만든 미추적 파일도 변경 파일 목록과 지문에 포함하지만, Git diff 요약에는 미추적 파일 내용이 나타나지 않을 수 있다.

실패 후 재개하면 시도 번호를 올리고 이전 결과와 오류를 별도 이력에 남긴다. 세션 ID와 Worktree는 유지한다. 같은 요청 키 또는 복구 키의 반복 호출은 기존 실행을 반환하고, 같은 키에 다른 내용을 보내면 거부한다. 전송 결과가 불확실할 때는 저장된 복구 메시지 ID로 전달 여부를 대조하도록 구현했다.

## 실제 연동 검증 결과

총 네 개의 Codex 세션을 사용했다. 초기 연결 검증 두 개와 실행 생명주기 검증 두 개이며, 실패 복구는 생명주기 세션 중 하나를 재사용했다.

| 사례 | 실행 내용 | 관측 결과 |
| --- | --- | --- |
| 초기 RPC 흐름 | PLAN을 읽고 브랜치와 PLAN 식별자가 담긴 `POC_PROOF.md` 생성 | 파일 생성·재읽기, Worktree 소속과 계획 원본 일치 확인 |
| 초기 GUI 흐름 | 화면에서 요청을 생성하고 `GUI_PROOF.md` 작성 | 입력 검증, 실행 중 중복 제출 방지, 실제 세션 이동 확인 |
| 성공 흐름 | `sum(a,b)` 구현 후 두 조건 검사 | `sum(2,3)=5`, `sum(-2,2)=0` 모두 통과. 종료 코드 0, 시도 1에서 완료 확정 |
| 의도적 실패 흐름 | `increment(n)`이 n을 그대로 반환하도록 결함 주입 | 원래 검사 `increment(1)=2`에서 `1 !== 2` 발생. 종료 코드 1과 실패 로그 저장 |
| 실패 복구 흐름 | 같은 세션에 재개 지시를 보내 반환값을 n+1로 수정 | 원래 테스트 1개 통과. 종료 코드 0, 시도 2에서 완료 확정 |
| 재시작과 재호출 | supervisor를 포함한 daemon 재시작 후 조회·재호출 | 완료 판정과 이전 실패 결과 유지, 동일 세션·Worktree·시도 번호 확인, 원래 테스트 재통과 |

성공 사례의 완료 판정은 GUI에서, 실패 복구 사례의 판정은 검증 스크립트의 RPC로 수행했다. 재시작 뒤 GUI에서 두 카드의 `완료` 상태와 판정 근거를 확인했다. 화면의 `자동 검증 1/1 통과`는 등록된 테스트 파일 검사 한 건을 뜻한다. 그 파일 안의 개별 테스트 수는 성공 사례 2개, 복구 사례 1개다.

복구 전후 `feature.test.mjs`의 SHA-256은 다음 값으로 같았다. 실패를 해결하기 위해 테스트의 기대값을 바꾸지 않았음을 확인하는 근거다.

```text
ac419489fa43b8ab51e67c33cd6df419abcab32cbc465745cb03ec53dba4a3aa
```

초기 연결 검증 두 건은 새 상태 모델에서 `awaiting-review`로 남아 있다. 해당 기록에는 자동 검사가 등록돼 있지 않으므로 자동으로 완료 처리하지 않았다. 최종 생명주기 검증 두 건은 모두 `completed`다.

### 자동 검사와 모의 테스트

최종 구현에서 타입 검사와 자동 테스트 12개가 통과했다. 별도의 실제 연동 검증 명령 두 개도 통과했다.

| 구분 | 확인한 내용 |
| --- | --- |
| 시작 흐름 테스트 4개 | 동시 중복 요청, 세션 생성 실패 후 재시도, 같은 키의 다른 입력 거부, 입력·저장 경로 검증 |
| 실행 생명주기 테스트 7개 | 실행·권한 대기·완료 판정, 실패 후 복구와 증거 보존, 오래된 결과·변경 파일 판정 거부, Hook 누락·중단·오래된 이벤트 처리, 전송 불확실성 대조, 구버전 기록 변환, 명시적 재검증 |
| 검증기 테스트 1개 | Windows 공백 경로에서 Node 테스트 실행, assertion 실패 전달, 파일 쓰기 차단 |
| `verify` | 초기 두 사례의 PLAN·Worktree·증거 파일과 재호출 결과 확인 |
| `verify:lifecycle` | 최종 두 사례의 판정·실패 증거·복구 테스트 불변성과 재호출 결과 확인, 원래 테스트 재실행 |

권한 대기, 중단 Hook, 전송 결과가 불확실한 복구는 모의 Runtime으로 검증했다. 실제 네트워크 단절이나 프로세스 강제 종료를 주입한 장애 시험은 수행하지 않았다. 성공·의도적 assertion 실패·동일 세션 복구·정상 재시작은 실제 연동으로 검증했다.

## 발견한 문제와 조치

| 문제 | 조치와 결과 | 남은 고려 사항 |
| --- | --- | --- |
| Codex 실행 시 `registered Core launch requires an installed app` 오류 | 설치된 앱 번들의 실행 파일을 사용하고, 독립 daemon supervisor를 두 데스크톱 실행 선택 변수 없이 다시 시작해 도구 실행을 확인했다. | 앱 업데이트로 실행 파일의 버전별 경로가 바뀔 수 있어 설치 경로 탐색·환경 진단이 필요하다. |
| Windows Node 테스트 검색에서 절대 경로를 찾지 못함 | Worktree를 cwd로 두고 `./feature.test.mjs`처럼 상대 경로를 전달했다. 두 실제 사례를 재검증해 성공과 의도적 assertion 실패를 구분했다. | 검증기 자체 오류와 사용자 코드 실패를 구분하는 표시를 MVP에서 개선할 수 있다. |
| 호스팅 Paseo 웹 앱에서 로컬 연결 시간 초과 | 같은 버전의 공식 bundled web UI를 localhost에서 사용해 화면 검증을 완료했다. | 호스팅 웹 앱의 연결 실패 원인은 미확정이다. 프로토타입의 접속 방식을 결정해야 한다. |

Codex 환경 조정은 독립 daemon에 전달되는 프로세스 환경에 한정했다. 전역 환경 변수, 사용자 Codex 설정, Windows sandbox와 승인 정책은 변경하지 않았다. 재현 절차는 `scripts/start-paseo.ps1`에 보존했다.

## 구현 구조와 보존된 데이터

UI, 애플리케이션 흐름, Paseo 연결, 저장·검증을 분리했다. 실행 정책은 애플리케이션 계층에 두고 외부 도구 호출은 어댑터로 연결한다.

| 구성 | 역할 |
| --- | --- |
| `client/screens`와 `client/components` | 요청 입력, 진행 상태, 결과·검증 근거, 판정과 재개 화면 |
| `shared/contracts` | 입력과 저장 데이터의 Zod 스키마, RPC 계약 |
| `server/domain` | REQ·TASK 식별자와 두 PLAN 생성 |
| `server/application` | 시작 순서, 상태 전이, 완료 판정, 복구, 요청별 잠금 |
| `server/adapters/paseo` | Worktree 생성, Codex 세션 시작·관찰·재개 |
| `server/adapters/storage` | 원자적 JSON 교체 저장, 파일 증거 수집, 독립 검사 |

요청 기록에는 입력과 계획 원본, workspace·세션·Worktree 식별자, 현재 상태, 최신 결과, 이전 시도, 상태 전이, 복구 체크포인트, 판정과 근거가 포함된다. 상태 전이 이벤트는 최근 100개까지 저장한다. 시작·상태 조회·재개·판정은 같은 요청별 잠금을 사용하며, 이 잠금은 단일 Plugin 인스턴스 안에서 동작한다.

## PoC의 한계와 MVP 설계 입력

| 현재 한계 | MVP에서 결정할 사항 |
| --- | --- |
| 요청 하나에 TASK 하나이며 계획은 템플릿으로 생성 | 첫 버전도 단일 작업으로 제한할지, 계획 편집·확인 단계를 추가할지 |
| 로컬 JSON과 인스턴스 내부 잠금 사용 | 저장소 방식, 데이터 버전 변경, 여러 프로세스의 동시 접근 지원 여부 |
| 누락 상태 보완은 화면·RPC 조회 시 수행 | 화면을 닫은 뒤에도 상태를 갱신하는 백그라운드 처리 필요성 |
| 자동 검증은 Node 내장 테스트와 문자열 검사만 지원 | 지원 언어·빌드 도구, 검증 어댑터와 실행 권한 범위 |
| 테스트를 작업 에이전트가 작성하며 최종 검토가 필요 | 완료 조건별 검증 근거, 테스트 신뢰성, 판정 책임과 화면 흐름 |
| 현재 지문은 HEAD와 Git 변경·미추적 파일을 기준으로 하며 ignored 파일은 제외 | 산출물 포함 범위, 검증 후 변경 감지, 승인 대상 버전 고정 방식 |
| 최종 응답 조회는 최근 timeline 100개 항목 | 장시간 실행의 결과 조회, 증거 보존·검색 방식 |
| 실제 강제 종료·네트워크 장애·장시간 부하 시험 미실시 | 재연결, 타임아웃, 중단, 자동 재시도 한도와 장애 시험 |
| 비용·지연·처리량 목표를 측정하지 않음 | 사용량 표시와 프로토타입 수용 기준 |

현재 Node 검사에는 검사당 최대 10초, 검증 루프의 20초 예산을 적용한다. Git 증거 수집과 통신까지 포함한 전체 응답 시간 보장은 아니다. 증거 대상은 파일당 2 MiB 이하, 최대 300개이며, 검사 출력은 마지막 16,000자, 최종 응답은 마지막 32,000자를 보존한다.

검증 프로세스는 Worktree 파일 읽기를 허용하고 파일 쓰기·자식 프로세스를 차단한다. 이 설정은 신뢰할 수 없는 임의 코드를 위한 완전한 보안 격리 또는 네트워크 차단을 보장하지 않는다. 범용 검증 명령을 추가할 때 실행 경계를 함께 설계해야 한다.

MVP 설계는 검증된 **요청 등록 → 단일 작업 실행 → 결과 검토 → 실패 재개** 흐름을 기준으로 시작하는 것이 적절하다. 위 표는 다음 설계 단계의 결정 목록이며, 기능 범위와 우선순위 확정은 별도 MVP 설계에서 수행한다.
