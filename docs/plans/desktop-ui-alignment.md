## 목표

### 최신 실행 상태 · 2026-11-26

U1~U6를 완료했다. 포함 화면 13개와 보조 설정·기존 이력 접근을 실제 WinUI 합성 호스트에서 확인하고, 기준 커밋의 네 Pivot 화면을 같은 fixture로 다시 실행해 전후 비교했다. 800×600·1280×900·1600×1000, 밝은/어두운 테마, 입력 유지·키보드 포커스·하단 행동 접근, 빈 목록·오류·로딩 복귀·권한/충돌/부분 반영 표시를 확인했다. 시험 도우미의 2초 대기와 5초 로딩 fixture 불일치를 10초 대기로 수정하고 재빌드(경고/오류 0)·모의 19개·GUI 복귀를 재확인했다. 제품 기능 코드는 이번 검증 재개에서 변경하지 않았다.

사용자는 2026-11-26 “배율은 굳이 지금 검증할 필요 없어. 어차피 항상 화면배율 100%에서 할 거야”라고 지시했다. 이에 V07의 배율 변경 시험은 이번 완료 조건에서 제외한다. 사용 목표는 100%이나 실제 이번 관측은 125%이며 100/150/200%를 통과로 기록하지 않는다. [화면별 수용 근거](../evidence/desktop-ui-alignment/20261126-ui-001/README.md)와 [최종 결과](../decisions/desktop-ui-alignment.md)를 따른다. 실제 모델 제작·콘솔 부재·트레이 수명 등 상위 G01~G11의 독립 검증은 완료로 확대하지 않는다. D4~D6는 미착수이며 커밋·push는 하지 않았다.

### 이전 실행 상태 · 2026-11-17

U1~U5의 UI 코드를 적용하고 앱/시험 호스트 빌드(경고·오류 0), 타입 검사, 모의 19개, 격리 C# 13개(skip 0)를 통과했다. U0 변경 전 작업실/설정 화면만 확보했으며, 변경 후 GUI 창 탐색에서 물리 Escape 입력으로 컴퓨터 유스가 중지되어 U6 시각 수용은 대기한다. 이후 Computer Use 호출은 하지 않았다. [구현 및 검증 중간 기록](../decisions/desktop-ui-alignment.md)에 정확한 범위·재현·미실행 항목을 남겼다. 상위 PLAN의 상세 단계로 `active`를 유지하며 전체 완료로 판정하지 않는다. 아래 최초 조사/계획 작성 단계의 미착수·GUI 금지 문구는 승인 이전 이력이다.

현재 작업실의 긴 탭·입력 나열을 저장된 와이어프레임의 프로젝트 중심 탐색, 화면별 목적, 본문/요약 영역, 주요 행동 배치에 맞춘다. 현재 사용할 수 있는 기획·코딩 제작 기능과 모든 복구·검토·반영 기능은 그대로 접근 가능해야 한다.

UI 정합은 이미지의 예시 기능을 모두 구현하는 일이 아니다. **현재 기능과 안전 조건을 유지하면서 화면 구성·스타일·표시를 바꾸는 것**이 목표다. 미구현 기능, 예시 수치·프로젝트·경로는 실제 기능이나 데이터로 복제하지 않는다.

## 현재 근거와 확인할 사항

### 조사 방법과 한계

- [와이어프레임 PNG 14개](desktop-transition.md#와이어프레임-참고-이미지)를 직접 열어 확인했다. 기준 디렉터리는 `docs/evidence/desktop-transition/20261116-wireframe-capture-001/`이다. 2배 캡처 이미지이므로 PNG의 픽셀 수치를 WinUI 논리 크기로 그대로 옮기지 않는다.
- 현재 [MainWindow.xaml](../../desktop/Orchiva.Desktop/MainWindow.xaml), [ProductionWorkspace.xaml](../../desktop/Orchiva.Desktop/ProductionWorkspace.xaml), [공통 테마](../../desktop/Orchiva.Desktop/Themes/Orchiva.xaml), 각각의 code-behind와 [DesktopViewModel](../../desktop/Orchiva.Desktop/DesktopViewModel.cs)을 대조했다.
- 기존 D1 [프로젝트](../evidence/desktop-transition/d1-20261116-003/03-project-light.png), [이력](../evidence/desktop-transition/d1-20261116-003/01-history-light.png), [어두운 설정](../evidence/desktop-transition/d1-20261116-003/04-settings-dark.png) 화면을 직접 확인했다. 이는 D2~D3 이전의 역사적 화면이며 현재 작업실의 렌더링 근거가 아니다.
- 현재 D2~D3 화면은 XAML·표시 코드로 구조를 확인했다. 앱 실행, 새 화면 캡처, 컴퓨터 유스, daemon 시작, 모델 호출은 하지 않았다. 실제 잘림·대비·포커스·스크롤·DPI 문제는 아직 관측하지 않았으므로 위험 항목으로만 기록한다.
- 당시 화면 설계 문서의 “앱 구현 미착수”는 시안 작성 시점의 상태다. 현재 구현 계약은 D2~D3 완료 기록이 우선하며, 최신 화면을 검증 완료한 것으로 표현하지 않는다.
- 조사 입력의 해시·기존 이벤트 연결·검증 기록은 [조사 근거](../evidence/desktop-ui-alignment/20261117-plan-001/summary.json)에 보존한다.

### 공통 차이

1. 시안은 프로젝트 선택·작업 시작·PLAN 이력·지침을 좌측에서 탐색한다. 현재 `MainWindow`는 작업실·기존 MVP 프로젝트·기존 v2 이력·연결 상태·설정으로 구성되어 있다.
2. 현재 `ProductionWorkspace`는 `프로젝트·지침`, `요청·PLAN`, `실행·결과 검토`, `결과물·소스 반영`의 네 Pivot에 서로 다른 목적의 화면을 합쳤다. 시안의 프로젝트 목록·분야 선택·문서 확인·결과 검토 구분과 다르다.
3. 현재는 대부분 단일 StackPanel이며, 시안의 입력 본문/설정 카드, 파일 목록/편집기, 파일 선택/비교 영역 구분이 없다. 수평 StackPanel과 최소 너비가 있어 좁은 창에서 잘릴 가능성은 있으나 실측하지 않았다.
4. 주요 버튼이 긴 본문 사이에 흩어져 있다. 시안의 화면별 제목·설명·하단 행동 영역과 다르다.
5. 결과·검사·검토 이력은 `ResultText`에 문자열/JSON으로 합쳐지고, 지침은 ComboBox로 선택한다. 데이터의 성격을 구분하는 카드·목록·상태 표현이 부족하다.
6. 공통 리소스는 제목 28, 절 제목 18, 보조 본문, 페이지 여백 28의 네 항목이다. 카드·상태·입력 그룹·행동 영역의 공통 스타일과 반응형 규칙이 필요하다.

## 범위

### 포함

- WinUI 3 네이티브 화면의 탐색·화면 구획·카드·목록·문서 영역·주요 행동 배치, 여백·폰트 계층·아이콘·밝은/어두운 테마·접근성.
- 동일한 기존 데이터를 화면용으로 나누는 읽기 전용 표시 모델과 컨트롤 바인딩. 화면 이동은 표시 상태이며 실행 상태 전이를 만들지 않는다.
- `MainWindow.xaml(.cs)`, `ProductionWorkspace.xaml(.cs)`, `Themes/Orchiva.xaml`, 필요할 경우 `DesktopViewModel.cs`와 예정 `desktop/Orchiva.Desktop/Presentation/`의 표시 전용 코드. 필요 시 순수 표시 코드의 집중 테스트와 테스트 프로젝트 연결 설정.
- 문구는 실제 동작에 맞춘다. 예를 들어 현재 앱 종료 후 제작은 실행부에서 계속되므로 설정의 오래된 “제작 단계에서 확정” 안내는 현재 계약에 맞게 정리하되 동작은 바꾸지 않는다.

### 제외

- `server/`, `shared/contracts/`, `bridge/`, `desktop/Orchiva.Bridge/`, entry point, SDK/런타임/배포/저장 스키마·프로젝트 템플릿 변경. 디자인을 위해 새 RPC나 새 영속 필드를 만들지 않는다.
- 모델·제공자·PLAN 생성·실행·검사·권한·복구·결과 판정·내보내기/소스 반영 정책 변경, 기능 삭제, 기존 명시적 확인 생략.
- 밸런싱·QA·레벨 디자인·게임 프로필·LLM 커스텀·파인튜닝. 최근 대화는 아이디어 논의이며 이번 UI 범위에 합의된 기능으로 포함하지 않는다.
- D4~D6, 새 미디어 미리보기, 파일/폴더 선택기, 새 검색·필터·자동 저장, 영속 초안 복원. 와이어프레임의 합성 데이터·시험용 상태 선택기·장식용 타이틀바를 제품에 복사하지 않는다.
- 이번 계획 작성에서는 앱/daemon 실행·세션/Worktree 생성·재시작·장애 주입·GUI 조작·원격 push를 하지 않는다. 이후 UI 검증에서도 모델 호출·신규 Agent/Worktree 생성은 기본 0건으로 잡는다. 운영 프로젝트/RNG는 시험 대상이 아니다.

### U1의 상세 구현·검증·완료 조건

1. 현재 이름 있는 컨트롤과 Action Tag를 목록화한다. 옮긴 컨트롤이 기존 handler에 정확히 한 번 연결되는지 비교하고, 기존 v2 조회·가져오기 경로도 유지한다.
2. 프로젝트 선택·작업 시작·PLAN 이력·지침을 프로젝트 중심 탐색으로 구성하고 연결/설정을 보조 영역에 둔다. 기존 MVP/v2는 이름을 명확히 한 보조 진입점으로 남긴다. 미구현 질문 항목은 비활성 안내만 제공한다.
3. 기본 제목 28/절 제목 18을 유지하고 본문·보조 설명·경로 텍스트의 역할을 정의한다. 간격은 8/12/16/24/32 DIP, 카드 여백 16~24 DIP, 모서리 8 DIP를 초기 구현 기준으로 사용한다. WinUI ThemeResource를 사용하고 임의 고정 밝은 배경/검은 글씨 조합을 피한다. 새로운 브랜드·폰트 패키지는 도입하지 않는다.
4. 넓은 화면은 본문 약 2/3·요약 약 1/3로 시작하고, 콘텐츠 가용 폭 900 DIP 미만에서는 단일 열로 전환한다. 탐색은 창 폭에 맞춰 접으며, 버튼은 필요한 경우 줄을 바꾼다. 800×600에서 주요 행동을 키보드/스크롤로 접근할 수 있어야 한다. 상하 공간을 확보하기 위해 앱 제목/페이지 제목을 중복해서 크게 표시하지 않는다.
5. 주요 행동은 본문과 구분된 하단 행에 배치한다. 높이가 작은 창에서는 해당 행도 접근 가능한 스크롤 흐름으로 전환해 본문을 가리지 않게 한다. 승인·실행 등 명령의 조건과 호출 순서는 그대로 둔다.
6. 단일 Workspace 인스턴스를 유지하며 화면 이동 자체는 표시 전환만 수행한다. 기존 명시적 선택/새로 고침에 연결된 조회와 주기 관측을 보존하고, 새로운 자동 조회·수정 호출을 붙이지 않는다.
7. `npm run desktop:build` 성공과 diff 범위 확인, 이벤트/입력/명령 대응표 검토를 마친다. GUI 미실행 상태에서는 U1 구현·정적 확인까지만 기록한다. 실제 넓은/좁은 화면·테마 확인을 마쳐야 U1 시각 수용 완료로 표시한다.

최초 계획 작성 당시에는 V01과 소스/기존 이미지 읽기 조사만 수행했다. 아래 GUI 대기 문장 역시 승인 전 이력이다. 이후 구현·검증 결과는 최신 실행 상태와 실행 기록을 따른다. UI만 변경하면 비용 있는 `desktop:production` 전체 모델 실행이나 과거 데이터 의존 verify/lifecycle을 관례적으로 실행하지 않는다. 타입/서버 변경이 새로 필요하면 이 PLAN의 기능 불변 범위를 벗어난 것으로 기록하고 별도 판단한다.

컴퓨터 유스는 기존 사용자 지시로 대기한다. GUI 검증 재개 또는 사용자의 수동 검증 근거가 생기기 전에는 V06~V08을 미실행으로 남긴다. 최신 WinUI 화면을 보지 않은 상태에서 정적 빌드만으로 디자인 완료를 선언하지 않는다. 시험용 UI 응답으로 실제 프로세스나 모델을 조작한 것처럼 기록하지 않는다.

## 실패 처리와 복원

- 화면 분리 중 상태/명령 소유권이 나뉘거나 handler가 두 번 호출되면 다음 화면으로 확대하지 않고 해당 UI 분리부터 수정한다. backend 조건을 완화해 화면을 통과시키지 않는다.
- UI에서 필요한 정보가 기존 응답에 없으면 미확인/후속 기능으로 남긴다. 준비됨·검증 통과·소스 반영 성공을 추정하지 않는다.
- 기능 변경이 필요한 차이는 위 제외 목록에 추가하고 원래 기능을 유지한 표현으로 조정한다. 예: 앱 내 PLAN 편집 대신 원문과 외부 수정 다시 읽기.
- 작업별 기준 커밋과 diff를 보존해 이번 UI 변경만 되돌릴 수 있게 한다. 프로젝트 docs·요청·원본 소스·과거 근거를 삭제하거나 복구 대상으로 덮어쓰지 않는다.
- GUI를 재개할 때는 새 격리 실행 ID/시험 설정을 사용한다. 원래 sandbox·운영 프로젝트의 요청으로 승인·반영·중단을 시험하지 않는다. 프로세스가 필요하면 소유권이 확인된 시험 home만 사용하고 정리 증거를 남긴다.
