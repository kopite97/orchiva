# M0 실행 기반 확인

- 상태: `completed`
- 작성일: 2026-11-12 · Asia/Seoul
- 관련 설계: [MVP 설계](../design/mvp-design.md)의 M0, 구현 시작 시 해소할 의존 사항
- 선행 조건: [하네스](../../AGENTS.md), 기존 PoC 소스·증거, 로컬 Paseo 환경
- 실행 근거: 2026-11-12 사용자가 초기 커밋과 작성된 M0 계획의 구현·검증을 지시했다. 소스 기준 커밋은 `7a675a918408419e5a245da4e086c04bced4716c`다.
- 소스: 기본 소스 폴더 `orchiva-plugin`, 원격 `https://github.com/kopite97/orchiva.git`

## 목표

M1의 명령·상태 모델과 M3의 백그라운드 동기화가 의존할 실행 기반을 실제 환경에서 확인한다. 브라우저나 최초 RPC 없이 연결을 시작하고, 재시작·응답 유실 뒤 외부 리소스를 대조하며, 확인한 커밋으로 Worktree를 생성하고, Plugin 종료 시 연결과 타이머를 정리할 수 있어야 한다.

M0의 결과는 작은 실행 어댑터와 재현 가능한 시험, 확인된 API·제약·채택 정책이다. 완성된 MVP 상태 머신이나 백그라운드 스케줄러를 이 단계에서 구현하지 않는다.

## 현재 근거와 확인할 사항

아래 표는 착수 당시 근거다. 구현·검증 후 확정한 결과는 [M0 결정과 증거](../decisions/m0-runtime-foundation.md)에 기록했다.

| 확인한 근거 | 현재 의미 | M0에서 확인할 사항 |
| --- | --- | --- |
| [index.server.ts](../../index.server.ts)는 RPC·Hook 컨텍스트에서 `paseo`를 받음 | 화면 조회와 Hook에 실행 관측이 연결됨 | Plugin cold start에서 독립 연결을 열 수 있는가 |
| 설치된 SDK의 `PluginServerContext`에 직접 `paseo` 속성이 없음 | 초기화 시 컨텍스트를 그대로 사용할 수 없음 | 지원되는 클라이언트의 초기화·인증·해제 경로 |
| [verify.mjs](../../scripts/verify.mjs)는 `createHostClient`와 `createPaseoApi` 사용 | 별도 Node 프로세스의 로컬 접속 경로가 존재 | 동일 경로가 Plugin 로드 환경에서도 작동하는가 |
| [runtime.ts](../../server/adapters/paseo/runtime.ts)는 생성에 `idempotencyKey`, 재개에 `messageId` 사용 | 기본 재호출 방지 수단이 있음 | daemon·Plugin 재시작과 응답 유실 뒤 중복 제거 범위·조회 가능성 |
| 현재 관측은 timeline 최근 100건에서 복구 메시지를 검색 | 검색 창 밖 메시지는 보이지 않을 수 있음 | 추가 페이지 조회 또는 다른 식별 조회가 가능한가 |
| 현재 Worktree 생성은 `refName: baseRef` 사용 | 움직일 수 있는 브랜치를 넘김 | 고정 SHA로 생성하고 실제 HEAD를 검증할 수 있는가 |
| 현재 Plugin cleanup은 Hook 해제만 수행 | 새 연결·루프의 종료 경계는 없음 | 연결·타이머·구독을 중복 없이 정리할 수 있는가 |
| 소스 Git이 새 원격에 연결됨 | 소스와 sandbox를 분리해 관리할 기반이 생김 | 실제 구현 전 기준 커밋 또는 복구 가능한 소스 백업 확보 |

API 선언이 있다는 사실은 실제 동작·재시작 내구성의 증거와 구분한다. 설치 버전은 실행 시작 시 manifest·lockfile·실제 모듈을 대조하여 기록한다.

## 범위

포함 범위는 연결 소유권을 가진 작은 어댑터, 시험용 시작·종료 경로, 외부 생성·전송의 대조 실험, 고정 커밋 생성 검증, 결과 보고와 후속 계약 제안이다. 필요하면 사용 중인 client 패키지를 직접 의존성으로 명시하고 lockfile을 갱신한다. 버전은 검증한 SDK와 맞춘다.

M0 구현에 포함하지 않는 항목은 v2 운영 데이터 마이그레이션, 완성된 명령 큐·프로젝트 슬롯, 주기적인 전체 요청 처리, 신규 UI, 제품 수준 자동 복구, 저장소 변경·자동 push·merge다. 기존 PoC 4건은 회귀 검증에 사용하고 새로운 장애 시험 대상으로 사용하지 않는다.

실제 시험에는 sandbox의 새 Worktree와 Codex 세션 생성, 해당 시험 클라이언트의 연결 차단, 시험 소유 프로세스 종료와 독립 daemon 재시작이 포함된다. 계획 작성 후 사용자의 구현 지시에 따라 아래 실행 기록의 범위에서 수행했다.

## 작업 순서와 산출물

### M0 1 기준점과 시험 경계 확보

1. 소스 Git 상태·remote·브랜치와 기준 커밋 존재 여부를 확인한다. 초기 커밋이 없으면 검토한 소스의 로컬 기준 커밋 또는 백업을 확보하고 그 식별자를 기록한다. 비밀값·`node_modules`·실행 데이터는 제외한다.
2. 소스 저장소와 sandbox의 실경로·remote·Git common-dir를 각각 기록한다. 시험 Worktree가 sandbox 소속인지 기존 검사를 재사용한다.
3. 기존 PoC 요청·결과·판정·세션·Worktree ID와 테스트 해시를 기준 증거로 확보한다. 변경 가능한 관측 시각 등과 보존해야 할 증거를 구분한다.
4. daemon의 home·주소와 활성 작업을 점검한다. 무관한 실행이 있으면 재시작·강제 종료는 하지 않고 정적·모의 작업부터 수행한다.
5. 새 실행 ID를 `m0-<날짜>-<고유값>`으로 만들고 시험 manifest에 대상 리소스·소유 PID·단계·키를 저장한다. 재실행 시 같은 시험 복원과 새 시험 생성을 명시적으로 구분한다.

산출물은 실행 환경 표, 소스 복구 기준점, 원본 PoC 증거 요약, 시험 manifest다. 인증 파일의 내용은 수집하지 않는다.

### M0 2 브라우저 없는 연결과 수명 검증

1. 설치된 공개 API와 기존 검증 스크립트를 읽어 `createHostClient`, `createPaseoApi`, 인증 콜백, `connect`·`close` 또는 실제 제공되는 dispose API의 소유 관계를 확인한다.
2. 연결 소유 어댑터를 작성한다. 후보 파일은 `server/adapters/paseo/connection.ts`다. 인터페이스는 시작, 연결 상태, API 접근, 종료를 제공하되 실제 SDK 확인 후 확정한다.
3. 먼저 단독 probe에서 접속·관측·정리를 확인하고, 이어 Plugin의 명시적인 시험 모드에서 초기화 경로를 검증한다. 시험 모드는 기본 비활성으로 두고 전역 환경을 수정하지 않는다.
4. 브라우저를 열지 않고 `request.list` 등 Plugin RPC도 호출하지 않은 채 daemon을 시작한다. Plugin 시작 시각 이후에 대상 세션 관측이 이루어졌음을 별도 증거로 남긴다. 단독 스크립트만 접속한 결과로 이 항목을 통과시키지 않는다.
5. daemon이 아직 준비되지 않은 경우 제한된 재접속 대기와 종료 중 취소를 확인한다. 등록 함수가 접속을 기다리며 daemon 시작을 막지 않도록 한다.
6. 정상 종료·연결 실패·Plugin reload에서 연결·타이머·구독을 정리한다. cleanup을 두 번 호출해도 안전해야 한다. reload 전후 자신의 연결·루프 수가 증가하지 않아야 한다.

독립 연결이 Plugin 실행 환경에서 지원되지 않으면 그 제약을 기록한다. 공식 지원 경로를 찾지 못한 채 최초 GUI 요청에 의존하는 방식으로 성공 처리하지 않는다. 별도 프로세스가 필요하면 배포 구조 변경의 영향과 대안을 설계에 반영한 뒤 해당 범위에서 진행한다.

### M0 3 고정 커밋의 Worktree 생성

1. sandbox 기준 브랜치에서 완전한 commit SHA를 구해 manifest에 저장한다. 로컬에서 이미 존재하는 서로 다른 두 커밋이 있으면 비교 입력으로 활용한다.
2. 생성 API에 SHA를 전달하고 생성된 Worktree의 `HEAD`가 정확히 그 SHA인지 확인한다. 현재 API가 SHA를 허용하지 않으면 지원되는 대안을 조사하고 전용 임시 ref의 필요 여부와 정리 책임을 기록한다.
3. 기본 `main`을 움직이지 않고 시험 전용 ref를 사용하여 계획 확인 이후 ref가 바뀐 상황을 재현한다. 다른 커밋을 만드는 fixture가 필요하면 시험용 Worktree에서만 명시적인 로컬 fixture로 만든다. 사용자 작업 브랜치와 원격에는 반영하지 않는다.
4. 저장한 SHA로 생성되는지 또는 계획 불일치가 명시적으로 거부되는지 확인한다. 최신 브랜치로 조용히 대체되는 동작은 실패다.
5. 생성 응답이 유실된 경우 같은 키·상관 식별자로 외부 workspace를 대조하고 Git 소속·HEAD·경로를 확인한다.

### M0 4 생성과 전송의 불확실성 대조

workspace 생성, agent 생성, 재개 메시지를 별개 효과로 시험한다. 각 효과 전 의도·키·대상 관계를 manifest에 저장한다. 아래 경계를 모의 시험으로 분리하고, 대표 사례는 실제 서버에서 효과가 발생한 뒤 응답만 차단하여 재현한다.

| 경계 | 주입 위치 | 복원 시 관측할 것 |
| --- | --- | --- |
| B1 | 의도 저장 후 전송 전 | 생성·전송이 실제 없음을 확인하거나 확인 불가로 분류 |
| B2 | 서버가 효과를 반영한 후 호출자 응답 전 | 존재하는 workspace·agent·메시지를 찾아 재사용 |
| B3 | 응답 수신 후 로컬 확인 기록 전 | 재시작 뒤 같은 리소스로 수렴하고 새 효과를 만들지 않음 |
| B4 | 확인 기록 완료 후 같은 키 재호출 | 같은 대상 또는 저장된 결과 반환, 효과 수 유지 |

실제 서버 반영을 확인하지 않은 단순 클라이언트 예외를 B2 실제 연동 증거로 간주하지 않는다. 생성 시험은 리소스 목록과 키·대상 관계를, 메시지 시험은 `clientMessageId`와 해당 turn 또는 메시지 수를 증거로 남긴다. 각 대표 시험은 연결 재수립과 정상 daemon 재시작을 포함한다.

최근 100건 밖에 있는 메시지와 `없음`, `관측 불가`를 구분하는 테스트도 작성한다. 대량의 유료 모델 실행 대신 모의 timeline으로 경계를 검사하고 실제 API의 페이지 조회를 별도로 확인한다. 실제로 재현하지 않은 긴 이력은 모의 증거로 표시한다.

대조 결과는 다음 세 가지로 정규화한다.

| 결과 | 허용할 처리 |
| --- | --- |
| `found` | 관계·내용·대상을 검사한 뒤 기존 효과에 연결 |
| `absent` | 부재가 권위 있는 조회로 확인되었거나 내구성 있는 중복 제거가 검증된 경우에만 같은 의도 재전송 |
| `unknown` | 전달 확인 대기로 유지. 자동 재전송·새 세션·새 작업 생성 금지 |

같은 키에 다른 payload를 보냈을 때 SDK와 서버가 어떻게 처리하는지도 통제된 시험으로 확인한다. 공급자가 거부하지 않더라도 Orchiva 명령 계층에서 입력 해시를 확인해야 한다는 후속 계약을 명시한다.

### M0 5 종료와 장애 복원 및 결과 정리

1. 정상 cleanup, Plugin reload, 연결 실패 중 종료를 모의·실제 경로에서 확인한다. 종료된 어댑터의 예약 작업이 이후 상태를 쓰지 않아야 한다.
2. 실제 강제 종료는 소유가 확인된 시험 클라이언트 또는 Plugin 프로세스에만 주입한다. 강제 종료에서 cleanup 실행을 기대하지 않고 다음 시작의 manifest 대조로 복구한다.
3. 시험 모드를 해제하고 정상 Plugin 로드 상태로 복원한다. 자신이 시작한 시험 프로세스를 확인하여 종료하고, 장애 원인으로 남긴 연결 차단을 해제한다.
4. 기존 `typecheck`, `test`, 두 `verify` 명령으로 회귀를 확인한다. 실행 전 보존한 기존 증거와 대조한다. 외부 호출 때문에 갱신될 수 있는 필드와 불변 증거를 구분하여 비교한다.
5. API 지원 표, 시험 결과, 미확정 항목, M1·M3·M5가 사용할 계약을 기록하고 설계의 가정을 확인된 선택으로 갱신한다.

### 파일별 변경

아래 파일을 구현했다. 고정 SHA 생성은 `pinned-workspace.ts`, 메시지 대조는 `reconciliation.ts`, Plugin 시험 관측은 `m0-probe.ts`로 분리했다. `effect-checkpoint.ts`는 직렬 호출용 최소 계약이며 v2 명령 저장소가 아니다. `track-execution.ts`에는 미확정 복구의 자동 재전송 차단을 적용했다. 응답 유실 시험에는 `scripts/m0-response-proxy.mjs`를 추가했다.

| 파일 또는 영역 | 구현 내용 |
| --- | --- |
| `server/adapters/paseo/connection.ts` | 독립 연결·인증 접근·수명 관리 |

| `server/application/ports.ts` | 연결·관측·대조의 최소 포트. v2 전체 계약은 M1로 미룸 |

| `server/tests/paseo-connection.test.ts` | 연결·종료·취소·중복 초기화 테스트 |

실제 스크립트는 `npm run m0 -- <단계> --run-id <실행 ID>`로 호출한다. 준비는 `init`, `inspect`, `assert-idle`; 생성은 `workspace`, `agent`, `send`; 관측 수명은 `probe-on`, `probe-off`, `probe-report`; 장애는 `fault-workspace`, `fault-agent`, `fault-message`, `crash`, `connection-failure`; 대조는 `verify`, `verify-faults`, `verify-crash`, `verify-uncertain`; 기타 시험은 `base-ref`, `replay`, `conflicts`, `history`, `wait`다. `crash-child`는 부모가 호출하는 내부 단계이며 `audit-legacy-refresh`는 이번 사전 원본 백업 없는 최초 manifest만의 명시적 차이 기록이다. 인수가 없으면 help만 출력한다. GUI 기능 변경은 없으므로 화면 배치 검증은 M0 대상이 아니며 V02의 브라우저 미사용 조건만 확인한다.

증거는 실행별 manifest와 비밀값을 제거한 결과 요약으로 보존한다. 필수 항목은 실행 ID, 소스 기준점, SDK 버전, 시험 대상·키·입력 해시, 주입 경계, 전후 리소스 수, 시간, 실제 결과와 오류다. 로컬 원본 경로는 결과 문서에 기록하고 인증 정보는 포함하지 않는다.

## 실패 처리와 복원

- 연결이 지원되지 않으면 계속 새 세션을 만드는 방식으로 우회하지 않는다. 공개 API 경로·프로세스 경계의 대안을 비교하고 필요한 설계 변경을 기록한다.
- 부재를 확정하지 못하면 `unknown`으로 보류한다. 리소스를 삭제하고 처음부터 재생성하는 방식으로 시험을 통과시키지 않는다.
- 시험 중 다른 사용자의 활성 작업을 발견하면 해당 daemon의 중단·재시작을 중지한다. 독립적으로 가능한 조사·모의 검증을 계속하고 실제 시험의 제약을 기록한다.
- 종료 대상 PID는 실행 manifest의 소유 정보와 프로세스 시작 시각을 재확인한다. 이름으로 모든 Codex·Node·Paseo 프로세스를 종료하지 않는다.
- 정상 종료로 복원한 뒤 시험 모드·구독·연결 차단을 해제한다. 소스 rollback은 시작 시 확보한 기준점으로 이번 변경만 대상으로 한다. 기존 사용자의 변경을 되돌리지 않는다.
- 기존 요청 JSON과 실패 증거, 시험 manifest·미확정 리소스는 보존한다. 시험 리소스의 정리는 소유·상태·증거 보존을 확인한 별도 절차로 수행하며 M0 완료를 위해 강제 삭제하지 않는다.

## 완료 조건

- [x] 브라우저와 최초 Plugin RPC 없이 시작한 연결·관측이 실제 Plugin 환경에서 확인됨
- [x] connection 초기화·취소·cleanup·reload에서 자원 누적이 없고 소유 관계가 문서화됨
- [x] 확인한 commit SHA로 Worktree를 생성하거나 불일치를 거부하는 경로가 실제로 검증됨
- [x] workspace·agent·message 각각의 재호출·응답 유실·재시작 동작과 한계가 기록됨
- [x] 부재·발견·불확실을 구분하고 불확실 상태에서 중복 실행하지 않는 정책이 검증됨
- [x] V01~V11 수행 결과와 근거가 있으며 미실행 필수 항목이 없음
- [x] 기존 PoC 네 요청의 의미·식별자·검사 기준·실패 증거가 보존됨. 초기 미승인 2건의 최신 결과 envelope 재수집은 [보존 한계](../decisions/m0-runtime-foundation.md#기존-poc-증거-대조)로 별도 기록
- [x] 정상 실행 환경으로 복원하고 M1·M3·M5에 넘길 계약과 결정을 기록함
- [x] 제품 설계·이 계획·목록을 함께 갱신함

안전한 `unknown` 처리는 해당 장애 사례의 유효한 결과다. 다만 모든 정상 연결에서도 조회·대조를 할 수 없거나 시작 시 연결 자체가 불가능하면 M0 목표를 충족하지 못한 것이다. 이 경우 원인을 해결하거나 근거 있는 설계 변경 후 필요한 검증을 수행한다.

## 결정과 후속 작업

로컬 인증을 사용하는 `createHostClient`·`createPaseoApi` 연결, 효과 전 의도 기록, 불확실할 때 보류, 고정 SHA와 생성 후 검증을 채택했다. workspace·agent 동일 키는 시험에서 같은 ID로 수렴했지만 복원 메시지의 client ID는 소실될 수 있다. M0의 연결은 시작 재시도·종료까지이며 운영 중 재접속은 M3 범위다.

M1에는 명령 상태·외부 참조·오류 분류·실행 슬롯 복원에 필요한 필드를, M3에는 연결 수명·시작 순서·재접속·종료 계약을, M5에는 메시지 조회와 안전한 재전송 조건을 넘긴다. 이 계획 작성만으로 후속 단계에 착수하지 않는다.
