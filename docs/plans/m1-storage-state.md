# M1 저장·상태·명령 이력과 실행 슬롯

- 상태: `completed`
- 작성일: 2026-11-12 · Asia/Seoul
- 관련 설계: [MVP 설계](../mvp-design.md)의 데이터 모델, 저장·마이그레이션, 실행 슬롯
- 선행 조건: [M0 결과](../decisions/m0-runtime-foundation.md), 소스 기준 `4397aaf`
- 실행 근거: 사용자가 M0 제약을 반영한 다음 상세 계획 작성과 그 계획의 구현·검증을 지시했다. proposed 등록 후 같은 작업에서 활성화하여 구현·검증을 완료했다.

## 목표

결과 재수집·재검증·복구가 이전 결과와 판정을 지우지 않게 한다. 동일 명령을 반복하거나 서로 다른 요청을 동시에 시작해도 효과를 중복 생성하지 않는다. 저장 또는 전달 중단 뒤 불확실성을 보존하고, 기존 네 PoC 기록을 ID·상태·증거를 유지한 v2로 옮긴다.

## 현재 근거와 확인할 사항

- 현재 저장은 버전 없는 JSON이며 최신 `result`와 `decision`이 교체된다. `attempts`에는 복구 직전 결과만 남는다. M0에서 초기 미승인 두 결과가 목록 조회로 교체됐다.
- M0에서 메시지 client ID 소실을 확인했다. `pending`/`unknown`은 시간 경과나 텍스트 일치로 해제하지 않는다.
- 요청별 메모리 잠금만 존재한다. 다른 요청의 동시 시작, 다른 프로세스의 저장, 오래된 객체의 덮어쓰기를 차단해야 한다.
- 현재 UI·회귀 스크립트의 계약을 유지하기 위해 기존 평면 필드는 최신 상태의 호환 뷰로 남긴다. v2의 `results`, `decisions`, `attemptHistory`, `commands`를 이력의 원본으로 한다. 이전에 없던 상세 파일 증거·조건별 판정을 마이그레이션에서 만들어내지 않는다.

## 범위

포함: v2 계약과 명시적 v1 변환, 바이트 원본 백업, 원자적 저장·revision 비교, 손상/미래 버전 개별 진단, 결과·판정 불변 이력, 시도·명령 상태, 프로세스 소유권, 프로젝트→요청 잠금, 저장 상태에서 복원되는 단일 실행 슬롯, 기존 명령 연결과 실제 네 기록 마이그레이션.

M0 재발 방지를 위해 목록 조회의 외부 관측·검증을 이 단계에서 제거한다. Hook과 명시적 refresh는 유지한다. 조회·진행 화면, 페이지네이션, 운영 백그라운드 대조는 M3다. 초안·확인 계획·기준 SHA 연결은 M2, 상세 파일/조건별 증거는 M4, 미확정 전달의 사용자 해결과 초기 재시도 UI는 M5다. 원격 push·merge, 새 모델 실행, 무관한 daemon 중단은 하지 않는다. 실제 적용은 활성 작업 확인 후 Plugin reload로 수행한다.

## 작업 순서와 산출물

| 작업 | 변경할 파일 또는 예정 파일 | 수행 내용 | 다음 단계로 넘길 결과 |
| --- | --- | --- | --- |
| 1 | `shared/contracts/feature-request.ts`, `server/domain/record-v2.ts` | schemaVersion 2, revision, 조건·계획 출처, 결과·판정·시도·명령 이력. v1은 legacy 표시, 누락 이력 복원 주장 금지 | 호환 뷰를 가진 v2 영속 계약 |
| 2 | `server/adapters/storage/json-request-store.ts`, `directory-owner.ts` | 원본 SHA 백업→검증된 임시 파일 sync→rename. CAS·이력 변경 거부. 개별 오류와 건수·바이트 진단 | 안전한 마이그레이션·쓰기 경로 |
| 3 | `server/application/execution-slot.ts`, `request-locks.ts` | 프로젝트→요청 직렬화. 준비·실행·대기·검증·미확정 명령이 슬롯 점유. 손상 파일/복수 점유는 새 실행 차단 | 슬롯 복원·BUSY 근거 |
| 4 | start·track 유스케이스 | 외부 효과 전 키·해시·단계 저장, 과거 키 중복 검사 후 revision 검사, 미확정 생성/재개 보류, 결과·판정 누적 | 기존 PoC 명령의 v2 연결 |
| 5 | `index.server.ts`, RPC 계약 | 시작 소유권 획득, 종료 후 소유권 반환, 순수 목록 조회, 저장 진단 RPC | 중복 Plugin 거부·진단 접근 |
| 6 | `server/tests/*`, 예정 `scripts/m1-storage.mjs` | 손상·중단·경합·재시작·명령 재전송 시험과 실제 네 기록 보존 비교 | 재현 명령·비밀값 없는 결과 보고 |

프로세스 점유는 데이터 실경로의 SHA-256으로 정한 Windows named pipe의 독점 bind로 구현한다. OS가 프로세스 종료 시 반환하므로 오래된 PID/시간만으로 파일 잠금을 탈취하지 않는다. 초기 loopback 포트 방식에서 실제 포트 충돌을 발견하여 named pipe로 바꿨다. 비 Windows fallback은 loopback이며 이 플랫폼은 검증 대상이 아니다. 이 방식은 단일 로컬 PC 범위이며 네트워크 공유 저장소를 지원한다고 주장하지 않는다. Plugin 인스턴스마다 별도 소유자가 필요하다.

저장은 요청별 한 JSON 안에서 이력과 현재 상태를 함께 교체한다. 저장 단계의 write lock과 유스케이스의 project lock은 별도이며, 공개 유스케이스는 project→request→write 순서를 따른다. revision이 맞지 않으면 `REVISION_CONFLICT`; 이미 있는 결과/판정의 삭제·수정은 `IMMUTABLE_HISTORY`로 거부한다. 관측 오류만 바뀐 저장은 의미 revision을 올리지 않는다.

스크립트는 `npm run m1 -- help`, `npm run m1 -- backup <run-id>`, `npm run m1 -- verify <run-id>`로 구현했다. 새 유료 모델 실행이나 GUI 변경은 없으므로 해당 시험은 하지 않았다. 모델 실행의 동시성은 모의 runtime과 실제 저장·프로세스로 검증하고, 실제 Plugin의 읽기·마이그레이션·회귀는 별도로 수행했다.

## 실패 처리와 복원

마이그레이션 전에 원본을 보존한다. 손상·미래 버전은 덮어쓰지 않는다. 중단된 변환은 같은 원본 SHA 백업을 검증하고 재개한다. 실제 적용이 실패하면 정상 파일까지 되돌리지 않고 원인과 개별 진단을 먼저 확인한다. 이전 버전으로 복원해야 한다면 Plugin 쓰기를 중단하고 이번 백업을 확인한 뒤 요청별로 복원한다. 모호한 외부 효과는 unknown과 슬롯을 유지한다. 실제 시험 중 활성 작업이 있으면 reload를 미루고 독립 검증을 진행한다.

## 결정과 후속 작업

M1은 호환 필드와 v2 이력을 같이 저장한다. 후속 화면은 이력 ID를 기준으로 접근해야 한다. M0에서 소실된 과거 envelope는 복원하지 못했으며 이번 마이그레이션의 원본은 현재 존재하는 기록이다. M2는 계획 확인 계약, M3는 관측과 수집 분리·운영 대조, M4는 상세 증거·조건별 판정, M5는 안전한 사용자 복구 절차를 이어간다.

SDK 0.15.4의 contribution은 동기 등록 함수여야 한다. 비동기 등록 실패 후 모든 RPC·Hook이 소유권/마이그레이션 `ready`를 기다리는 방식으로 고쳤다. 소유권을 얻지 못한 인스턴스는 등록된 진입점에서 오류를 반환하며 작업하지 않는다. 기존 UI의 revision 없는 명령은 호환 경로이며 새 `request.revalidate`는 키·결과·revision을 요구한다.
