### 제외 및 권한 경계

브라우저 UI + 로컬 daemon을 유지한다. exe/설치 프로그램, 원격 접속, 다중 사용자·프로젝트·daemon 제품 지원, 병렬 TASK, 임의 shell 검사, 자동 Git 게시, 무인 수정·강제 슬롯 해제, Worktree 자동 삭제는 제외한다. 소스의 사용자 승인 Git push와 Orchiva가 생성하는 작업의 push·merge 금지는 별개다.

아래 절차는 현재 승인된 작업이다. 실행 ID는 `m6-20261113-001`이다. 기존 9개 요청의 전체 JSON과 project/runtime/daemon 설정 사본 및 SHA-256 manifest를 `%USERPROFILE%/.orchiva/m6/m6-20261113-001`에 보존했다. 인증 파일은 복사하지 않았다. 시험은 새 식별자와 격리 fixture를 사용한다. 가용 버전을 바꾸거나 모델·권한·보안 설정을 바꾸지 않는다.

## 시험 데이터와 실행 환경

1. 실행마다 `m6-<날짜>-<고유번호>`를 사용하고 사례별 token·명령 키를 분리한다. manifest의 중복 생성은 거부한다. 실패한 실행을 지우거나 같은 키의 입력을 바꿔 다시 시작하지 않는다.
2. 실행 전 `%USERPROFILE%/.orchiva/requests`의 전체 JSON, 관련 프로젝트/daemon 설정을 로컬 백업하고 SHA256·커밋·버전·작업 상태를 기록한다. 인증 파일 내용은 백업 묶음·출력·커밋에 포함하지 않는다. 기존 M0~M5의 격리 fixture 및 미확정 증거도 변경하지 않는다.
3. 모델 작업의 대상은 등록된 `C:/Users/USER/lib/orchiva-PoC`의 새 전용 Worktree뿐이다. 허용 remote는 `kopite97/PoC-sandbox`다. 소스 원격 `kopite97/orchiva`와 혼동하지 않는다. main 이동·기존 Worktree 수정·RNG 접근은 없다.
4. 정상 통합 GUI는 실제 Plugin을 사용한다. 손상 JSON·미지원 버전·100건 합성 데이터·미확정 장애는 실행별 **별도 store와 소유 시험 worker**를 우선 사용한다. 제품 유스케이스·저장·어댑터를 재사용하고 주입은 시험 composition에서만 한다. 현재 경로·연결 설정을 임의 환경 변수로 바꿀 수 있다고 가정하지 않으며, 필요한 주입 지점과 공개 API를 구현 첫 단계에서 확인한다.
5. 합성 데이터에는 시험 표시를 하고 실제 모델 결과로 집계하지 않는다. 격리 GUI의 client는 제품과 동일하게 사용하며 RPC 차이·worker 유무를 기록한다. 생략한 제품 경로를 검증했다고 주장하지 않는다.
6. 실제 daemon 장애는 소유 테스트의 PID·생성 시각·실행 경로·daemon home을 확인하고 무관한 active turn/권한 대기가 없을 때만 수행한다. 전역 프로세스 이름으로 종료하지 않는다. 전체 PC 방화벽·인터넷 연결을 변경하지 않고 시험 소유 연결 프록시만 끊는다.
7. 사례는 순차 실행한다. 계획한 실제 모델 리소스는 성능용 30개 요청과 통합/장애용 최대 10개 요청으로 **Agent·Workspace 각각 최대 40개**를 초기 상한으로 둔다. 같은 요청의 재개는 새 Agent를 만들지 않는다. warm-up·실패 잔여물도 이 상한에 포함하며 여유가 없으면 원인·측정 계획을 먼저 조정한다. 시간·모델 사용량을 무시한 자동 반복은 하지 않는다.

GUI는 1280×900과 390×844에서 빈 목록·필터·100건 다음 페이지·초안 이탈·네트워크 오류·관측 지연·질문/권한 대기·검토·실패·미확정·완료·과거 상세를 확인한다. 메모 유지, 중복 클릭 방지, 가로 넘침, 키보드 포커스와 checkbox 상태의 접근성 전달도 확인한다. 실제 질문/권한 대기를 재현하지 못하면 격리 UI 확인과 실제 미실행을 분리해 기록하고 실제 검증으로 표기하지 않는다.

### 장애 경계와 복원

모의 fixture로 모든 경계를 먼저 재현한 후 대표 실제 사례를 수행한다. 외부 효과 발생 여부를 추정하기 위해 임의 sleep 뒤 프로세스를 죽이지 않고, 시험 wrapper/IPC와 별도 읽기 연결로 경계 도달을 확인한다.

| ID | 중단/유실 위치 | 실제 시험 범위와 기대 동작 |
| --- | --- | --- |
| D01 | 의도 저장 전 / 저장 후 안전한 accepted·plans | 저장 전이면 효과 0. 안전한 준비 checkpoint는 같은 키·계획·SHA로 이어감. 격리 v2 writer 강제 종료·복원 |
| D02 | 외부 호출 phase 저장 후, 호출 여부가 미확정 | workspace/agent/message 각각 모의. 실제 소유 worker 대표 1건을 종료. 호출 증거가 없더라도 저장 phase만으로 미전송 판정하지 않고 unknown 유지 |
| D03 | 서버 효과 발생 후 SDK 응답 전달 전 | 실제 생성·재개 응답 프레임을 시험 프록시에서 각각 차단. 외부 목록/원래 messageId로 효과를 확인하고 같은 리소스 대조. 단순 예외 반환과 구분 |
| D04 | SDK 성공 응답 뒤 완료 checkpoint 저장 전 / 저장 뒤 호출자 응답 전 | 모의 전 대상 + 실제 재개 대표에서 소유 writer 종료. 재시작 후 found 또는 unknown으로 안전 수렴. applied 후 동일 명령 재호출은 추가 전송/쓰기 없음 |
| D05 | JSON temp write·flush 후 rename 전 / rename 직후 | 별도 store의 자식 writer 종료. 주 JSON은 이전/다음 유효 버전 중 하나, 부분 JSON·기존 결과 유실 없음. 임시 파일은 증거로 보존하고 잠금 회수는 프로세스 종료에 근거 |
| D06 | 실행/검증 중 daemon worker 강제 종료 | M6 작업만 활성일 때 정확한 worker PID를 종료하고 supervisor 동작을 관측. 같은 ID를 다시 조회하며 모델이 생존/중단했는지는 실측으로 판단. 새 Agent 자동 생성 금지 |
| D07 | 관측 연결 단절·정상 복귀, Plugin reload와 종료 경합 | 실제 시험 연결만 차단. 마지막 상태 보존, backoff, 한 cycle/연결만 존재, 종료 후 늦은 쓰기·타이머 부활 없음 |
| D08 | 세션/Worktree 유실·저장소 용량/쓰기 거부 | 유실 상태는 전용 격리 fixture로 먼저 검증. 실제 파일 시험은 M6 소유 경로만 가역적으로 이동/복원하고 agent 삭제·시스템 디스크 채우기는 하지 않음. 신규 전송 차단·증거 유지 |

D03/D04와 daemon 복원을 결합해 messageId가 소실되는 경우도 기록한다. 원문 유사성이나 timeout 경과로 성공·미전송을 선언하지 않는다. 이 경우 정확한 사유를 표시한 unknown과 슬롯 유지가 설계상 합격이며, 자동 복구 성공과는 별도 항목이다. 이 상태를 실사용 store에 남겨 다른 작업을 막지 않도록 미확정 시험은 격리 store에서 수행한다. 실제 Plugin 경로와 시험 worker 경로의 차이는 보고서에 명시한다.

### 성능과 30분 운영

측정 전에 지표·자료형·샘플 조건을 고정한다. 경과 시간은 단조 시계, 여러 프로세스 간 상관관계는 요청 ID·이벤트 ID와 UTC 시각으로 기록한다. 관측 간격으로 생기는 오차 상한도 남긴다.

| ID | 데이터·절차 | 목표와 판정 |
| --- | --- | --- |
| P01 | 격리된 실제 JSON store 100건: 초안 60·실패 20·완료 20. 실행 결과가 있는 40건은 각 결과 3개, 검사 로그 16KB·응답 8KB·파일 10개를 기본 분포로 생성. 스키마/불변 참조 유효성 확인. 초안 갱신·첫/다음 목록·상세 각각 warm-up 5회 후 신규/조회 표본 30회 | 저장·목록·상세 각각 p95 ≤1초. 실제 RPC 직렬화·반환과 현재 상세 전체 payload 포함. large-history 별도 스트레스 수치를 기본 목표와 혼합하지 않음 |
| P02 | 신규 start 30회와 신규 resume 30회를 실제 Plugin·SDK로 순차 측정. 30개 최소 작업 요청을 만들고 각 종료 후 같은 세션에 한 번 재개. 기능 시험을 표본에 포함하려면 동일 측정 조건을 먼저 만족해야 함 | 각각 p95 ≤2초 접수 목표. 동일 키 replay나 BUSY 응답은 신규 접수 표본에서 제외하고 별도 집계 |
| P03 | 정상 연결에서 외부 상태가 조회 가능해진 시각→저장 상태 전이→GUI 반영. Hook 경로와 Hook 없는 5초 대조 경로를 나눠 최소 10회씩 | 저장 상태 반영 ≤10초. GUI 지연 별도 보고. 통제된 검사 진행 시 validating 관측 가능. 전체 모델 실행시간과 혼합하지 않음 |
| P04 | 정상 daemon 재시작 3회와 D06 장애 재시작 1회 이상. 연결 완료 시각과 초기 대조 완료 또는 구체적 unknown 사유 표시 시각을 비교 | 연결 성립 뒤 ≤30초. 연결 자체의 지연도 별도 표시. 구체적 이유 없는 복원 대기는 실패 |
| P05 | 외부 변경 없는 안정 요청과 통제된 관측 대상에서 30분 연속 운영. 10초 간격 샘플, reload/단절은 별도 장애 구간으로 분리 | 완료/안정 결과 재검증 0, 결과/판정/시도 유실 0, 동시 cycle 최대 1. 종료 뒤 시험 연결·타이머 0. RSS/heap·CPU·cycle·쓰기 수 추세를 보고 |

P01 기본 데이터의 실제 총 byte·결과 수·응답 크기를 manifest에 저장한다. 시드와 생성 규칙을 고정하되 합성 100건을 실제 100개 에이전트 사용 실적으로 표현하지 않는다. 첫 요청의 cold 값을 따로 기록하고 warm-up을 본 표본에 섞지 않는다. 기본은 정상 idle 상태, 실행·검증 잠금 경합 조건은 별도 30회 측정하여 초안 저장 가능 여부와 지연을 함께 확인한다.

P02는 최소 입력과 고정 모델/검사로 수행하고 fresh command와 idempotent replay를 따로 집계한다. 시작 preflight 및 재개 verifyResources/observe/send의 지연을 모두 구간별 기록한다. **의도 저장 완료, SDK 응답, 최종 RPC 응답**의 시간을 각각 남긴다. 현재 resume은 send를 기다리므로 내부 저장 2초만 보고 사용자 응답도 2초라고 주장할 수 없다. 측정상 차이가 있으면 먼저 원인을 기록하고, 접수와 전송 분리가 필요할 때에만 durable pending·중복 방지·재시작 복원 계약을 유지하는 최소 수정을 계획에 추가한다. 변경 시 장애 시험과 신규 30개 표본을 다시 검토한다.

통계는 n·성공/실패/timeout 수·min·p50·p95·max를 기록하며 p95는 정렬한 n개 중 ceil(0.95×n)번째 값이다. 30개면 29번째 값이다. 실패·timeout은 삭제하지 않고 별도로 전부 보고하며 필요한 성공 표본이 모자라면 미충족이다. outlier를 임의 제거하지 않는다. 하드웨어·OS·전원 상태·백그라운드 작업·커밋·SDK/모델·시험 시작/끝 시각도 기록한다.

30분 측정의 메모리 증가만으로 누수 확정/부재를 선언하지 않는다. 첫 안정 5분과 마지막 5분 구간, 연결/타이머/쓰기 횟수를 대조한다. 자원 수가 누적되거나 메모리가 계속 증가하면 원인을 조사하고 동일 조건 추가 측정을 수행한다. 모델 대기 시간·비용·다중 사용자 처리량은 SLA로 제시하지 않는다.

### 회귀 및 문서 검증

구현을 허용받은 뒤 현재 명령 `npm run typecheck`, `npm test`, `npm run verify`, `npm run verify:lifecycle`, M2/M3/M5의 보존 실행 verify를 수행한다. M4 verify는 해당 과거 Worktree를 임시 편집하므로 이번의 새 통합 장애 재료로 사용하지 않는다. M4 원본은 해시로 보존 대조하고 같은 기능은 A08/A16의 신규 M6 사례에서 검증한다. M0/M1의 과거 장애 명령도 그대로 재실행하지 않는다.

`npm run m6 -- help`가 실행 가능한 M6 명령의 현재 목록이다. `d06-recover`는 D06의 기존 실패 요청만 같은 Agent/Workspace로 재개한다. 문서의 일반 사용 절차와 개발자 전용 M6 명령을 혼합하지 않는다. 문서는 상대 링크·코드 블록·인코딩·명령 존재·계획 상태를 확인한다.

첫 사용 흐름은 개발자가 상태 JSON을 수정하지 않고 GUI와 안내로 수행해야 한다. 에이전트가 안내를 따라 한 경우에는 자동 검증으로 기록하고 실제 사용자의 사용성 평가로 대신하지 않는다. 사람의 첫 사용 수용이 필요한 최종 단계는 사용자의 실제 확인 결과를 별도로 남기며, 미수행이면 그 상태를 표시한다.

## 실패 처리와 복원

- 무관한 활성 세션, 허용 remote 불일치, baseline 해시 불일치, PID/소유권 불확실, 이미 사용한 run ID가 있으면 그 단계의 외부 효과를 시작하지 않는다. 진행 가능한 문서·격리 테스트와 차단된 실제 시험을 구분한다.
- 각 장애 전에 대상·checkpoint·기대 영향·복구 명령을 manifest에 저장한다. 종료 신호 후 실제 exit를 확인하고 남은 supervisor/agent 상태를 조회한다. 종료 요청 성공만으로 프로세스 종료나 모델 중단을 가정하지 않는다.
- 응답 timeout 뒤 새 명령 키를 만들어 전송하지 않는다. 원래 명령·외부 ID로 대조한다. 전달을 증명하지 못한 상태는 증거와 함께 보존한다.
- daemon config·Plugin 등록·프록시·임시 포트·시험 계측의 변경 목록을 보관한다. 종료 시 시험 항목만 되돌리고 현재 사용자 변경과 원본 설정 차이를 확인한다. 기존 요청 JSON을 통째로 덮어써 정상 상태를 흉내 내지 않는다.
- 새 Worktree/Agent·실패 로그·중간 JSON·검사 파일·미확정 기록은 보존한다. 임시 코드·소유 연결은 종료하되 원본 시험 증거를 자동 청소하지 않는다. 파일 이동은 M6 소유 경로의 실경로와 허용 범위를 확인한 뒤 같은 셸에서 수행한다.
- 필수 수용 실패·중복 외부 효과·기존 증거 유실은 완료 차단이다. 원인 수정 뒤 영향받는 A/P/D 항목과 회귀를 다시 수행한다. 목표 초과를 결과에 맞춰 몰래 완화하지 않고 원래 목표·실측·원인·수정/범위 결정 근거를 함께 남긴다.

## 결정과 후속 작업

- M6는 사용자의 2026-11-13 구현·남은 사항 전체 실행 지시에 따라 수행했고 `completed`다.
- 응답 유실·강제 종료·연결 오류·모델 중단은 서로 다른 결과로 보고한다. 확인 불가를 안전하게 유지하는 정책과 정상 복구 성공을 혼합하지 않는다.
- 성능은 실제 사용자 RPC와 내부 의도 저장을 함께 측정한다. 현재 구현이 목표를 만족한다고 미리 결론 내리지 않는다.
- 최종 A01~A16, D01~D08, P01~P05 판정은 실제/모의 범위와 함께 결과 문서에 연결한다. 실제 질문/권한 요청, 새 PC 설치, 장기 운영 및 더 정밀한 GUI 지연은 후속 검증이며 이를 실제 통과로 표시하지 않는다.
- 불변 이력·단일 실행 슬롯·고정 SHA·명령 중복 제거·sandbox 제한을 유지한다. 수용 시험을 쉽게 만들기 위한 테스트 기대값 변경이나 외부 효과의 검증 생략은 하지 않는다.
- 수용 항목을 완료할 수 없거나 실제 연동이 환경 조건으로 막히면 합격으로 표시하지 않고 차단 원인·대체 증거·남은 절차를 기록한다.
